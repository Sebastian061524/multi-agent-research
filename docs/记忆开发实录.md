## 一、项目概览

### 目标

调研 Agent 跑完一次就「忘了」，下次遇到同一个主题会**从头再查一遍**。
要解决两件事：

1. **它调研过什么** —— 会话摘要，避免重复劳动
2. **用户想要什么** —— 用户偏好，让报告长成用户要的样子

### 最终能力清单

| 能力 | 存在哪 | 谁写入 | 谁读取 | 作用 |
|---|---|---|---|---|
| **会话摘要** | `memory.db` 的 `sessions` 表 | 系统自动（跑完就写） | `plan_node` | 规划时避开已调研过的角度 |
| **用户偏好** | `memory.db` 的 `preferences` 表 | 用户显式命令 | `write_node` | 控制报告风格/结构 |
| **断点续跑** | `checkpoints.db` | LangGraph `SqliteSaver` | 框架 | 中断后接着跑，不重跑已完成的节点 |

### 技术栈

| 组件 | 用什么 | 为什么 |
|---|---|---|
| 存储 | **SQLite**（标准库 `sqlite3`） | 几十~几百条，不需要服务、不需要额外依赖 |
| 语义检索 | **BGE `bge-small-zh-v1.5`**（复用主项目已加载的模型） | 零额外成本 |
| 相似度 | **NumPy 点积**（向量已归一化） | 不用向量数据库，`mat @ qv` 就够 |
| 会话状态 | **LangGraph `SqliteSaver`** | 官方 checkpointer，天然支持中断/续跑 |

### 与主项目的关系

```
main.py 的检索能力（完全不动）
        ↓ 复用
memory/memory_store.py（新增数据层）
        ↓ 两个卡点
plan_node  ← 读会话摘要        （影响「怎么拆问题」）
write_node ← 读用户偏好        （影响「怎么写报告」）
        ↑ 一个写入点
跑完调研 → save_session()      （只记事实）
```

**关键约束**：不改动任何检索逻辑；不改动原有图结构，只多接两条读写线。

## 二、背景知识：Agent 的记忆是什么

### 2.1 一句话定义

> **Agent 的记忆 = 跨调用/跨会话存活下来的信息，而且它必须能改变 Agent 的行为。**

后半句是重点。一条记忆如果永远不会导致不同的行为，它就不是记忆，是垃圾数据。
**这是本项目所有取舍的判据。**

### 2.2 记忆不是一块，是三层

| 层 | 存活范围 | 本项目用什么 | 例子 |
|---|---|---|---|
| **上下文窗口** | 单次 LLM 调用 | `State` 里传的东西 | 本次的资料片段 |
| **会话状态** | 同一个 `thread_id` | LangGraph checkpointer | 上次拆的子问题、报告草稿 |
| **长期记忆** | 跨会话、跨进程 | SQLite + 语义检索 | 上个月调研过 ReAct |

**容易混的地方**：checkpointer 常被叫「记忆」，但它只管**同一个会话**。换一个 `thread_id` 就完全隔离。
真正的「长期记忆」要自己建，本项目就是 `memory.db`。

### 2.3 ⭐ 记「事实」还是记「结论」——核心设计原则

| | 事实 | 结论 |
|---|---|---|
| 例子 | 「2026-10-08 调研过 ReAct 架构的优缺点，拆了 3 个子问题」 | 「ReAct 比 Plan-and-Execute 更适合长任务」 |
| 会错吗 | 不会 | **会**（当时的资料/判断可能有误） |
| 会过时吗 | 不会 | **会**（技术半年就变） |
| 出错的后果 | 无害 | **错误被永久固化，还会被后续会话当成前提继续放大** |

**本项目只记事实，不记结论。** 这条原则直接决定了表结构：
`sessions` 表存 `topic` / `sub_questions` / `report_head`，**没有一个字段存「判断」**。

### 2.4 有哪些「候选记忆」，为什么砍掉大部分

第一版列了 6 个候选，最后只做 2 个。用 2.1 的判据筛：

| 候选 | 记了会怎样 | 结论 |
|---|---|---|
| 会话摘要 | 规划时避开已查过的角度 | ✅ **做** |
| 用户偏好 | 报告按用户要的风格写 | ✅ **做** |
| 关键结论 | 可能错、会过时、错误累积 | ❌ 不做 |
| 知识库变动 | 可以自动检测，属于「系统状态」不是「记忆」 | ❌ 不做（该检测就检测） |
| 交互习惯（爱问什么） | 样本太少，推断不可靠 | ❌ 不做 |
| 用户画像 | 同上，而且猜错了很烦人 | ❌ 不做 |

**砍掉不是「以后再说」，是「有明确理由不做」。**

## 三、开发过程（8 个步骤）

### 步骤 1：先设计，不写代码 —— 四个问题

动手前先把这四个问题答完：

| 问题 | 本项目的答案 |
|---|---|
| **记什么** | 会话摘要 + 用户偏好（见 2.4 的筛选） |
| **存哪** | SQLite 两张表（不引入向量数据库） |
| **何时写** | 摘要＝跑完自动写；偏好＝用户显式命令 |
| **怎么用** | 摘要→`plan_node`；偏好→`write_node` |

**为什么先答这四问**：记忆功能最容易失控的地方是「什么都想记」。
先定死「记什么」，后面的表结构、写入点、读取点都是它的推论。

**写入时机的一个关键差异**：

```
会话摘要：跑完调研 → 系统自动写（零 LLM 成本，直接取 State 字段）
用户偏好：用户敲命令 → 显式写
```

摘要是「系统观察到的」，偏好是「用户告诉的」——**来源不同，写入方式就不同**。
偏好绝不能从对话里猜（猜错了很烦人），必须显式写入。

### 步骤 2：`memory/memory_store.py` —— 数据层

**设计要点**：把数据层和 LLM 层解耦。

```python
class MemoryStore:
    def __init__(self, db_path=DEFAULT_DB, embed=None):
        """
        embed: 编码函数，签名 (list[str]) -> np.ndarray
               应当返回【已归一化】的向量（这样点积就等于余弦相似度）
               不传则检索退化为关键词匹配
        """
```

**`embed` 可注入是这一步最重要的设计。** 带来三个好处：

1. **能单测** —— 不传 `embed` 走关键词兜底，秒级跑完，不需要加载模型
2. **能降级** —— 没有模型的环境仍然可用（虽然检索质量差）
3. **依赖倒置** —— 数据层不 import `sentence_transformers`，由调用方决定用什么模型

两张表：

```sql
CREATE TABLE IF NOT EXISTS sessions (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    thread_id     TEXT,
    topic         TEXT NOT NULL,
    sub_questions TEXT,          -- JSON 数组
    report_head   TEXT,          -- 报告开头（写库时截断到 300 字）
    created_at    TEXT NOT NULL
);

CREATE TABLE IF NOT EXISTS preferences (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    text       TEXT NOT NULL UNIQUE,   -- ← UNIQUE 天然去重
    created_at TEXT NOT NULL
);
```

**方法清单**：

| 方法 | 签名 | 说明 |
|---|---|---|
| `save_session` | `(thread_id, topic, sub_questions=None, report_head="") -> int` | 只存事实；`report_head` 内部 `[:300]` 截断 |
| `list_sessions` | `(limit=500) -> list[dict]` | 按 id 倒序 |
| `search_sessions` | `(query, top_k=3, min_score=0.5) -> list[dict]` | 返回项多一个 `score`；**同主题只保留最相关一条** |
| `add_preference` | `(text) -> bool` | 已存在返回 `False`（靠 `UNIQUE` 的 `IntegrityError`） |
| `list_preferences` | `() -> list[str]` | |
| `delete_preference` | `(text) -> bool` | |
| `stats` | `() -> dict` | `{"sessions": n, "preferences": m}` |

**`search_sessions` 里两处值得注意的实现**：

```python
# ① 语义检索：向量已归一化，所以点积 = 余弦相似度，不用算模长
qv  = np.asarray(self.embed([query]))[0]
mat = np.asarray(self.embed([r["topic"] or "" for r in rows]))
scored = [(float(mat[i] @ qv), r) for i, r in enumerate(rows)]

# ② 同主题去重：避免「同一个主题列 5 遍」
seen = set()
for score, r in scored:
    if score < min_score:
        break                    # ← 已排序，可以直接 break
    key = (r["topic"] or "").strip()
    if key in seen:
        continue
    seen.add(key)
    out.append({**r, "score": round(score, 4)})
```

### 步骤 3：关键词兜底 vs 语义检索 —— 用数据标定阈值

**目的**：确认两件事——① 关键词兜底够不够用 ② 语义检索的阈值该定多少。

**实验脚本**：`memory/step2_compare_search.py`

```python
os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")
model = SentenceTransformer("BAAI/bge-small-zh-v1.5", device="cpu")
embed = lambda texts: model.encode(texts, normalize_embeddings=True)
```

**踩坑：`huggingface.co` 连不上**

```
[WinError 10060] 连接尝试失败：HEAD 请求超时重试 5 次
```

修法（`main.py` 里其实早就有，写新脚本时忘了带）：

```python
os.environ.setdefault("HF_ENDPOINT", "https://hf-mirror.com")
# 加载时 local_files_only=True
```

**发现 1：关键词兜底有严重的假阳性**

```
查询「Agent 评测」
  → 命中「多 Agent 协作如何结合记忆机制与 RAG」  得分 0.75
```

原因：`_keyword_scores` 按**字符集合重合度**打分，`「Agent 评测」` 的字符几乎全在那条长主题里。
**字符重合 ≠ 语义相关。** → 证明关键词兜底只能当「无模型环境的降级方案」，不能当主力。

**发现 2：BGE 有「分数地板」**

5 条记忆、4 个查询的实测分数分布：

| 查询类型 | 分数 |
|---|---|
| 相关查询 | 0.5608 / 0.5000 / 0.4346 |
| **完全无关**（量子计算） | **最高 0.3575** |

无关文本也能拿到 0.29~0.36 —— 分数范围很窄（0.18~0.56），**没有一个「天然的 0」**。

**结论：`min_score = 0.40`** 能干净地分开四种情况，而且**不需要 reranker**。
（我原先预测「分界模糊，得靠重排器」，被数据推翻了。）

> ⚠️ 阈值必须**用真实数据量出来**。样本小时它只是「当前数据下的最优」，
> 数据变多、主题变化后要重调。

### 步骤 4：checkpointer 的五个实验

**目的**：搞清楚 LangGraph 的 checkpointer 到底怎么工作——这是「会话记忆」的基础设施。

**实验脚本**：`memory/step1_checkpointer.py`

| # | 实验 | 结果 |
|---|---|---|
| ① | 无 checkpointer，同一图跑 3 次 | 每次都 `['A','B']`（**完全不记得**） |
| ② | 有 checkpointer，同 `thread_id` 跑 3 次 | 累积成 `['A','B','A','B']`（**记得，但从头又跑了一遍**） |
| ③ | 换 `thread_id` | 完全隔离 ✅ |
| ④ | `graph.get_state(cfg)` | 返回 `values` / `next` / `config`（含 `checkpoint_id`，每次执行产生一个新 checkpoint） |
| ⑤ | `interrupt_before=["b"]` + `invoke(None, cfg)` | 停在 `['A']`，`next=('b',)` → 再跑得到 `['A','B']`，**A 没有重跑** ✅ 真断点续跑 |

**⭐ 实验 ② 和 ⑤ 的区别是这一步最值钱的认知：**

| 调用方式 | 行为 |
|---|---|
| `invoke({}, cfg)` | **从头跑**（只是带着旧状态）—— A 会重跑 |
| `invoke(None, cfg)` | **从断点续跑** —— A 不重跑 |

**判断「有没有没跑完的活儿」，看 `get_state(cfg).next`**：
`()` 空元组 = 跑完了；非空 = 停在断点，可以续。

**f-string 小坑**：想输出字面量花括号必须双写——

```python
print(f"invoke({})")     # ❌ SyntaxError: f-string: valid expression required before '}'
print(f"invoke({{}})")   # ✅
```

### 步骤 5：`main.py` 接入 checkpointer

```python
# checkpointer：把每一步的状态存进 SQLite，支持中断后接着跑
_ckpt_conn = sqlite3.connect(
    os.path.join(BASE_DIR, "checkpoints.db"),
    check_same_thread=False,          # LangGraph 可能在线程里用这个连接
)

PAUSE_BEFORE = "write"                # 演示用；正式使用设为 None
graph = builder.compile(
    checkpointer=SqliteSaver(_ckpt_conn),
    interrupt_before=[PAUSE_BEFORE] if PAUSE_BEFORE else None,
)
```

**`__main__` 里的会话选择逻辑**：

```python
thread_id = clean_input(input("会话 ID（回车用 default）：")) or "default"
config = {"configurable": {"thread_id": thread_id}}
snap = graph.get_state(config)

if snap.next:
    # 非空 = 上次没跑完 → 从断点继续
    print(f"\n🔁 检测到未完成的会话（下一步：{snap.next}）")
    show_stages(snap.values, skipping=True, next_nodes=snap.next)
    result = graph.invoke(None, config)          # ← 传 None = 续跑
else:
    # 空 = 新会话
    topic = clean_input(input("请输入调研主题："))
    result = graph.invoke({"topic": topic, "memory_context": memory_context}, config)
```

**四阶段状态汇报**（`show_stages`）——`⏭️ 本次跳过` / `✅ 已完成` / `▶️ 本次执行` / `⏸️ 尚未轮到`。
「本次执行」靠 `snap.next` 判断，不是靠猜。

**⭐ 踩坑：`KeyError: 'report'`**

收尾处直接写 `print(result["report"])` 会崩。根因：

> `interrupt_before` 会让 `invoke` **提前返回**，此时 State 停在 write **之前**，
> **根本没有 `report` 字段**。

修法——收尾先判断「跑完了没」，再决定输出什么：

```python
final = graph.get_state(config)
if final.next:
    print(f"⏸️  已暂停在断点（下一步：{final.next}）")
    print("   状态已存入 checkpoints.db。")
    raise SystemExit(0)
print(result["report"])
```

**这个 bug 顺带解释了三个此前的困惑**：
- 「第二次没有规划者提示」→ 正确，它被跳过了
- 「第一次也没看到规划者输出」→ 规划者跑了（checkpoint 里 `sub_questions` 从 0 变 3）但收尾崩溃打乱了输出
- 「报告没打印」→ 收尾代码缺失 + 崩溃

**一个 bug 能同时解释多个「看起来不相干」的现象。** 遇到这种情况，先怀疑它们有共同根因。

### 步骤 6：写会话摘要（跑完自动写）

加在 `main.py` 的**最末尾**：

```python
# ⚠️ 只记【事实】——调研了什么、拆了哪些子问题、报告怎么开的。
#    不记"结论对不对"（结论可能错、会过时，记下来会误导以后的会话）。
# ⚠️ 必须放在最末尾：上面的 `if final.next: raise SystemExit(0)` 保证了
#    「只有真正跑完才会走到这里」——断点时的状态是不完整的，不能写记忆。
memory = MemoryStore(
    MEM_DB,
    embed=lambda texts: model.encode(texts, normalize_embeddings=True),
)
memory.save_session(
    thread_id=thread_id,
    topic=result["topic"],
    sub_questions=result["sub_questions"],
    report_head=result["report"],
)
print(f"\n🧠 已记住这次调研（记忆库现有 {memory.stats()['sessions']} 条会话）")
memory.close()
```

**位置就是设计。** 「放在 `raise SystemExit(0)` 之后」不是随手写的——
它保证了**只有真正跑完的会话才会被记住**，断点时的残缺状态不会污染记忆库。

**验证**：

```
统计: {'sessions': 1, 'preferences': 0}
[1] 2026-10-08 17:26:45  thread=demo4  主题=ReAct 架构的优缺点  3 个子问题  report_head 已截断
```

③ `__main__` 新会话分支检索并传入：

```python
past = []

    memory = MemoryStore(MEM_DB, embed=...)
    past = memory.search_sessions(topic, top_k=2, min_score=0.40)
    memory.close()

memory_context = ""
if past:
    print("📚 这个主题以前调研过：")
    lines = []
    for h in past:

            lines.append(f"  当时拆的子问题：{'；'.join(h['sub_questions'])}")
    memory_context = "\n".join(lines)
```

#### ⭐ A/B 对照实验

**为什么必须做对照**：跑完 demo6 后发现子问题角度「变了」，但**「变了」≠「因为记忆」**——
LLM 本来就有随机性，多个变量同时在动。

先造一个开关隔离变量：

```python
USE_MEMORY = "--no-memory" not in sys.argv
```

**判据（沿用调研项目的方法论）：对照实验的差异点，必须只有实验组才会做得到。**

历史记忆（demo4「ReAct 架构的优缺点」）拆的方向：`Plan-and-Execute 优势` / `多 Agent + RAG 缺陷` / `记忆+可观测+评测`

| 组 | 拆出的 3 个子问题 | 与历史的关系 |
|---|---|---|
| **A（`--no-memory`）** | ① ReAct 相比 Plan-and-Execute 的推理-行动交错优势与适用场景<br>② 多 Agent 协作与 RAG 结合的主要缺陷与失败模式<br>③ 借助记忆机制与可观测性、评测方法量化评估 | **三个角度全部撞上历史** |
| **B（有记忆，`[1.0]`）** | ① 推理与行动交替中的**错误累积与循环问题** → 可观测性监控与定位<br>② 推理轨迹与行动轨迹的**耦合特性** → 记忆存储结构与检索方式的设计约束<br>③ 多 Agent 协作下独立决策 vs 集中规划 → 协作效率与任务一致性 | **三个角度全部避开历史**，且更具体深入 |

**「避开某个具体方向」只有知道那个方向存在才做得到** → 差异只能由记忆解释。

**诚实边界**（必须说清楚）：
- 样本量 = 1，数据强烈支持但不是铁证
- 要更硬，需要：重复 3~5 次 / 加大「避开」指令强度 / 把历史写成「已覆盖：A、B、C」的显式格式

**附带验证**：A/B 两组都停在 write 断点前 → `raise SystemExit(0)` → **记忆库没被污染**（`sessions` 仍是 1）。这同时验证了步骤 6 的「位置就是设计」。

### 步骤 8：用户偏好

**和步骤 6-7 的关键差异**：摘要是系统自动写的，偏好是**用户主动告诉的**。

| | 会话摘要 | 用户偏好 |
|---|---|---|
| 谁决定写 | 系统自动（跑完就写） | 用户显式命令 |
| 内容性质 | 事实（做过什么） | 意愿（想要什么） |
| 生效位置 | `plan_node`（怎么拆问题） | `write_node`（怎么写报告） |
| 条目数 | 每次调研 +1 | 手工维护，几条而已 |

#### 改动 1：`write_node` 注入偏好

**设计选择：`write_node` 里直接读 DB，而不是存进 `State`。**
理由：每次执行都重读 → **改完偏好立刻生效**，不用重开会话；而且 `write_node` 会因审校重写被多次调用，每次都拿到最新偏好。

```python
# ---- 读取用户偏好 ----
mem = MemoryStore(MEM_DB)        # 不传 embed：list_preferences 是纯 SQL，不需要向量
prefs = mem.list_preferences()
mem.close()

pref_block = ""
if prefs:
    pref_block = "\n【用户偏好 —— 请在不违背第 3 条的前提下尽量满足】\n" + \
                 "\n".join(f"- {p}" for p in prefs) + "\n"
```

插入 prompt 的位置：**第 4 条防幻觉规则之后、`【资料】`之前**。

```
要求：
1. 使用 Markdown 格式
2. 结构包含三部分：## 概述、## 分点论述、## 结论
3. **只使用提供的资料**，不要编造资料中没有的信息
4. 如果某个子问题的资料不足，在对应位置明确写出「资料未涵盖此部分」
{pref_block}
【资料】
```

**为什么放这个位置**：偏好可能和防幻觉冲突（用户写「多举具体例子」，但资料里没例子 → 模型可能编）。
把偏好排在防幻觉规则**后面**，并用「**在不违背第 3 条的前提下**」显式声明优先级。
**光靠顺序不够，那句话才是真正的保险。**

#### 改动 2：`--pref` / `--prefs` 命令行

加在 `USE_MEMORY` 之后、**第一个 `input()` 之前**——这两个命令是非交互的，不该被「请输入会话 ID」挡住。

```python

    mem = MemoryStore(MEM_DB)
    prefs = mem.list_preferences()
```

#### 改动 3：对照实验验证偏好真的生效

**问题**：端到端跑一遍，报告里确实出现了 Markdown 表格。

## 四、关键问题专题

### 专题 1：为什么不用向量数据库

**规模决定选型**：记忆条目几十~几百条。

| 方案 | 本项目需要吗 |
|---|---|
| 向量数据库（Chroma / FAISS 索引 / Milvus） | ❌ 几百条向量，加载 + 建索引的成本 > 收益 |
| NumPy 全量点积 | ✅ 几百条 × 几百维，微秒级 |

```python
qv  = np.asarray(self.embed([query]))[0]
mat = np.asarray(self.embed([r["topic"] or "" for r in rows]))
scored = [(float(mat[i] @ qv), r) for i, r in enumerate(rows)]
```

**前提**：`embed` 返回的向量必须**已归一化**（`normalize_embeddings=True`），
这样点积才等于余弦相似度，省掉算模长。

> **通用原则**：先量数据规模，再选存储方案。
> 「大家都用向量数据库」不是理由。

### 专题 2：阈值必须用真实数据量出来

**BGE 有「分数地板」**：完全无关的文本也能拿到 0.29~0.36。

| 查询类型 | 实测分数 |
|---|---|
| 相关 | 0.5608 / 0.5000 / 0.4346 |
| **完全无关** | **最高 0.3575** |

→ `min_score = 0.40`，干净分开。**不需要 reranker**（预测被数据推翻）。

**两条纪律**：
1. 阈值**不能在脑子里定**，要在真实数据上量
2. 样本小的时候，它只是「当前数据下的最优」——数据变多要重调

### 专题 3：`invoke({}, cfg)` 与 `invoke(None, cfg)` 不是一回事

**第一个参数叫 `input`，是「新输入」，不是「要不要继续」。**

LangGraph 把「数据」和「待办」分开存在 checkpoint 里：

| checkpoint 字段 | 含义 |
|---|---|
| `values` | **数据** —— 状态字段现在是什么值 |
| `next` | **待办清单** —— 还有哪些节点没执行 |

于是两种「空」在这里分道扬镳：

| 写法 | LangGraph 的理解 | 行为 |
|---|---|---|
| `invoke(None, cfg)` | 「我**没有**新输入」 | 读 `next` → 接着干待办 → **续跑** |
| `invoke({}, cfg)` | 「这是**新输入**，只是内容为空」 | 走正常流程 → **从 START 开始** |
| `invoke({"topic": "x"}, cfg)` | 「这是新输入」 | 从 START 开始 |

**实测证据**（`memory/step9_resume_semantics.py`，图结构 `START → A → B → END`，`interrupt_before=['b']`）：

```
实验 1：有断点时，第二次 invoke({}, cfg)
    第 1 次 invoke({}) 之后        values=['A']       next=('b',)
    第 2 次 invoke({}) 之后        values=['A', 'A']  next=('b',)   ← A 重跑，且又停了
    → 完全跑完了吗：False

实验 2：有断点时，第二次 invoke(None, cfg)
    第 1 次 invoke({}) 之后        values=['A']       next=('b',)
    第 2 次 invoke(None) 之后      values=['A', 'B']  next=()       ← A 没重跑，跑完了
    → 完全跑完了吗：True

实验 3：已经跑完（next 为空）之后再调 invoke(None, cfg)
    又调一次 invoke(None) 之后      values=['A', 'B']  next=()
    → log 没变（安全的空操作）
```

**⚠️ `invoke({}, cfg)` 在断点状态下会卡死在原地**：
每次调用都从 START 重跑 A，然后又停在 B 前面 —— `next` 还是 `('b',)`。
**不是「多跑一次」，是「永远跑不完」。**
而且它**静默**：不报错、`result` 也拿得到（里面是 `['A','A']`），只是报告永远出不来。

**完整对照表**：

| 场景 | `invoke({}, cfg)` | `invoke(None, cfg)` |
|---|---|---|
| 上次停断点（`next=('b',)`） | 从 START 重跑 → 又停在同一个断点 → **永远跑不完** | 从 b 接着跑 → **跑完** ✅ |
| 上次跑完（`next=()`） | 从 START 重跑一遍 | 什么都不做，返回现有状态 |

**这也是 `interrupt_before` 的核心用法**：`invoke` 会**提前返回**，
此时 State 是**残缺的**（停在 write 之前 → 没有 `report`）。
所有收尾代码都必须先检查 `final.next`。

### 专题 4：A/B 对照实验的判据

**问题**：跑完一次发现「行为变了」，但**「变了」≠「因为你改的那个东西」**。
LLM 有随机性，多个变量同时在动。

**判据（本项目用了两次）**：

> **差异点必须「只有实验组才会做得到」。**

- 步骤 7：A 组（不知道历史）撞上旧角度，B 组（知道历史）避开 → 「避开」只有知道才做得到 ✅
- 步骤 8：A 组 0 行表格，B 组 9~11 行 → 两组零重叠 ✅

**配套动作**：
1. **造开关隔离变量**（`--no-memory`）
2. **固定其他所有东西**（同一份 findings、同一个代码路径、同一个 topic）
3. **重复多次看区间有没有重叠**（随机性不能靠单次观察排除）
4. **说清楚样本量**（`n=1` 的数据强烈支持，但不是铁证）

### 专题 5：改返回结构时，`len()` 是一种静默失效

MCP 部分已经踩过：把 `search_knowledge` 的返回值从 `list[dict]` 改成 `dict` 后，
调用点的 `len(r1.data)` 语义从「段数」悄悄变成「**dict 的键数**」→ 输出「3 段」看起来完全合理。

**教训**：**返回值也是接口的一部分。改了返回类型的形状，就要找出所有取值处。**
`len()` 尤其危险——它对很多类型都合法，所以永远不会报错。

### 专题 6：不可见字符家族

| 案例 | 症状 | 诊断 |
|---|---|---|
| `from sympy import false` | `smart_query: bool = false` → Pydantic warning；`repr(false)` 打印出来是 `False`，**看起来一模一样** | `type(false)` 是 `BooleanFalse` |
| **BOM（`\ufeff`）** | PowerShell 管道输入的 thread_id 变成 `'\ufeffprefA'` | `repr(tid)` / `[hex(ord(c)) for c in tid]` |
| 零宽字符 | 字符串看起来对，比较不相等 | 同上 |
| `len(dict)` | 数值看起来合理，语义已经漂移 | 问「这个表达式对哪些类型合法」 |

**统一手法**：

```python
print(repr(x))                                        # 最常用
print([hex(ord(c)) for c in x if ord(c) < 32 or ord(c) > 0x2000])
```

> **凡是「看起来对但行为不对」的字符串，第一反应是 `repr()`。**

### 专题 7：BOM 要在「程序边界」修，不要在「调用方」修

**两次失败的过程**：

| 尝试 | 结果 |
|---|---|
| 第一次：以为是自己 PowerShell 变量用错 | 改了 `$OutputEncoding`，**BOM 还在** |
| 第二次：写成 `[System.Text.UTF8Encoding]::new($false)` | **BOM 还在，只是从 2 个变成 1 个** |

**根因重新定位**：问题不在「我有没有写对」，而在
**「管道喂给程序的输入，编码不由程序控制」** —— 换个 shell、换个调用方（CI、他人脚本）就又会出问题。

**正确的位置：程序边界。** 外部进来的字符串，进门先规范化：

```python
def clean_input(s: str) -> str:
    """规范化终端输入：去掉 BOM 等不可见字符

    用管道喂输入时（@("id") | python main.py）编码不由程序控制，
    第一行可能带上 \ufeff，导致 thread_id 查不到断点、还会被存进数据库。
    输入是「外部数据」，在边界处一次清干净，后面所有代码都不用操心。
    """
    return s.replace("\ufeff", "").strip()


thread_id = clean_input(input("会话 ID（回车用 default）：")) or "default"
topic     = clean_input(input("请输入调研主题："))
```

**双保险**：
- 程序侧：`clean_input()` 保证**新数据**干净
- 工具侧：`memory/fix_bom.py` 清理**已有数据**；`memory/inspect_db.py` 复查
- 脚本侧：`resolve_thread()` 按「去掉 BOM 后相等」查找，**不因为一个不可见字符就查不到**

> **通用原则**：数据校验放在**边界**（输入进来时），不要散落在每个使用点。
> 修调用方只能管住你知道的那个调用方。

### 专题 8：删除要覆盖所有引用该键的表

清理 BOM 时发现**上次「清理完成」是假的**：

```
checkpoints.thread_id: '\ufeffprefA'       → prefA   ✅ 这次修的
writes.thread_id:      '\ufeffprefA'       → prefA   ✅ 这次修的
writes.thread_id:      '\ufeff\ufeffdemoA' → demoA   ⚠️ 上次没删干净！
writes.thread_id:      '\ufeff\ufeffdemoB' → demoB   ⚠️ 上次没删干净！
memory.db sessions:    '\ufeffprefA'       → prefA   ✅ 这次修的
```

`checkpoints.db` 有**两张表**：`checkpoints`（状态快照）+ `writes`（节点写入记录）。
上次执行的 `DELETE FROM checkpoints WHERE thread_id LIKE '%demoA'` **只删了主表**，
`writes` 里的行成了**查不到也删不掉的幽灵数据**。

**教训**：

> **删一个「键」之前，先问「有多少张表引用了这个键」。**
> `DELETE` 执行成功 ≠ 删除完整。

这次的后果只是涨了点体积；但如果哪天按 thread 统计节点写入次数，**数字就是错的**。

**顺带一个通用检查手段**：清理脚本默认**只预览**，加 `--apply` 才真的改；
目标值已存在时跳过并警告（避免主键冲突把两条记录合并）。**破坏性操作先让人看一眼。**

### 专题 9：已跑完的会话不能原地重跑

**盲区**：`snap.next == ()` 有两种情况，很容易被当成同一种：

| `snap.next == ()` | `snap.values` | 真实含义 |
|---|---|---|
| 全新 thread_id | 空 | 🆕 真·新会话 |
| **已跑完的 thread_id** | 有 topic/report/findings | ⚠️ **旧会话重跑** |

而 `main.py` 原来的 `else` 分支不区分，一律打印「🆕 新会话，从头开始」。

**实测后果**：

```
第 1 次跑（全新 thread_id）
     findings = [{'question': '新问题'}]
     next = ()   ← 跑完了

第 2 次跑（同一个 thread_id）
     findings = [{'question': '新问题'}, {'question': '新问题'}]   ← 旧数据没清，累加上了
     topic    = 话题二                                          ← 这个被覆盖了
```

三层后果，一层比一层重：

1. **提示是错的** —— 明明跑过，却说「🆕 新会话，从头开始」，还要重输主题
2. **`findings` 翻倍** —— `findings: Annotated[list, add]` 带累加器（`main.py:43`）
3. **报告张冠李戴** —— `write_node` 把 `state['findings']` 全拼成 `materials`，
   于是报告里混进上一轮的资料，而 `topic` 已经换成新的 → **不报任何错**

触发条件很日常：**用一个跑完过的会话 ID 再跑一次。**

**为什么不能靠改 reducer 来修** —— `add` 是必需的：

```python
def fan_out(state: State):
    return [Send("research_one", {"question": q}) for q in state["sub_questions"]]
```

`fan_out` **并行**派发多个 `research_one`，每个都 `return {"findings": [...]}`：

| reducer | 结果 |
|---|---|
| `add` 累加器 | **合并**，三家都留下 ✅ |
| 无 reducer（覆盖语义） | **只剩最后完成的那个**，前面两次的调研结果全丢 ❌ |

而且在 `invoke` 里显式传 `{"findings": []}` 也救不了 —— 空列表 `add` 上旧数据，还是旧的。

> **结论：并行累积的字段天生没法「原地重置」，唯一正确的做法是「重跑必须换 thread_id」。**

**修法（`main.py` 的 `pick_thread_id()`）**：不去「清理」旧状态（清不掉），而是**换一个干净的地方重开**。

```python
def pick_thread_id(graph, base: str):
    """挑一个可以安全开跑的 thread_id，返回 (thread_id, config, snap)"""
    # 全新会话 / 有断点要续跑 → 直接用原来的 ID
    config = {"configurable": {"thread_id": base}}
    snap = graph.get_state(config)
    if snap.next or not snap.values:
        return base, config, snap

    # 已跑完 → 换一个带序号的 ID（base#2、base#3……直到找到干净的）
    n = 2
    while True:
        thread_id = f"{base}#{n}"
        config = {"configurable": {"thread_id": thread_id}}
        snap = graph.get_state(config)
        if snap.next or not snap.values:
            return thread_id, config, snap
        n += 1
```

加上调用点之后，`__main__` 的结构从两分支变成**三分支**：

| 状态 | 判断依据 | 行为 |
|---|---|---|
| 有断点 | `snap.next` 非空 | `invoke(None, config)` 续跑，**ID 不动** |
| 全新会话 | `next` 空 + `values` 空 | `invoke({...}, config)` 从 START |
| 已跑完 | `next` 空 + `values` 非空 | **自动换 `base#2`** → 落回「全新会话」 |

**验证 1**（`memory/step10_pick_thread_id.py`，合成图 + `MemorySaver`，**7/7 通过**）：

```

✅ 已跑完 → 换成 #2                      得到 't-fresh#2'     期望 't-fresh#2'
✅ 已跑完且 #2 被占用 → 换成 #3           得到 't-fresh#3'     期望 't-fresh#3'
✅ 新 ID 跑完后 findings 只有 1 条        得到 1               期望 1
✅ 新 ID 的 topic 是新主题               得到 '话题二'         期望 '话题二'
✅ 有断点 → 保持原 ID（交给续跑分支）      得到 't-pending'     期望 't-pending'
✅ 有断点 → 返回的 snap.next 非空         得到 True            期望 True
```

| # | 现象 | 根因 | 修法 |

| 1 | `AttributeError: 'MemoryStore' object has no attribute 'save'` | 方法名是 `save_session` | 按实际签名调用 |

| 8 | PowerShell 管道输入的 thread_id 变成 `'\ufeffprefA'` | **管道输入编码不由程序控制** | 程序边界 `clean_input()`；工具 `fix_bom.py`；脚本 `resolve_thread()` 容错 |

| 10 | `DELETE FROM checkpoints ...` 后 `writes` 表仍有残留 | **只删了主表** | 删除要覆盖所有引用该键的表 |
| 11 | 端到端看到表格，但不知是不是偏好的功劳 | 缺对照实验 | A/B 隔离变量 + 重复多次看区间重叠 |
| 12 | `MEM_DB` 定义在 `__main__` 里，`write_node` 用不了 | `if __name__ == "__main__"` 块的变量在 **import 时不执行** | 常量提到模块级（`main.py:23`） |
| 13 | `--pref 请用表格 别太长` 丢词 | 只取了 `sys.argv[idx+1]` | `" ".join(sys.argv[idx+1:])` |

## 六、经验教训

### 1. 先定「记什么」，再想「怎么记」

记忆功能最危险的失败模式不是「坏了」，是「记了一堆没用的东西，还持续污染后续会话」。
**判据：一条记忆必须能改变 Agent 的未来行为。答不出来就不记。**

### 2. ⭐ 记事实，不记结论

事实不会错、不会过时；结论会错、会过时，**而且错误会被固化后放大**。
本项目 `sessions` 表里没有一个字段存「判断」。

### 3. 位置就是设计

写记忆的代码放在 `raise SystemExit(0)` **之后**，不是随手放的——
它保证了「只有真正跑完的会话才会被记住」。
A/B 实验顺带验证了这一点（两组都停在断点，记忆库没被污染）。

### 4. 解耦数据层和模型层（`embed` 可注入）

`MemoryStore(embed=None)` 能秒级自测、能在无模型环境降级。
**依赖倒置不只是「设计模式」，它直接换来可测试性。**

### 5. 阈值要用真实数据量，不要靠直觉

实测推翻了两个预测：
- 「分界模糊，需要 reranker」→ 实际上 0.40 干净分开
- 「无关查询分数会很低」→ 实际上有 0.29~0.36 的地板

### 6. 「不报错」比「报错」更危险

`len(dict)` 永远合法、`state.get()` 永远不抛、`--prefs` 误匹配也照样跑。
**它们不会给你任何提示，只是安静地给出错误结果。**
识别方式：问「这个表达式/API 对哪些输入是合法的？我的输入是不是恰好也在里面？」

### 7. 输入校验放在边界

`clean_input()` 修在 `input()` 之后，而不是在每个使用点。
**修调用方只能管住你知道的那个调用方**（换 shell、换 CI 就又坏了）。

### 8. 成功 ≠ 完整

`DELETE` 执行成功，但只删了主表 —— 上次的「清理完成」是假的。
**破坏性操作之后要复查**（`inspect_db.py` 就是干这个的）。

### 9. 「变了」不等于「因为你改的东西」

LLM 有随机性，多个变量同时在动。
**判据：差异点必须只有实验组才会做得到。** 配套动作：造开关、固定其他变量、重复多次、说清样本量。

### 10. 一个 bug 可以解释多个「不相干」的现象

`KeyError: 'report'` 同时解释了三个困惑（没有规划者提示、报告没输出、崩溃）。
**遇到一堆症状时，先假设它们共享一个根因。**

### 11. 给已有结构的 State 加字段，要用 `.get()`

旧 checkpoint 里没有新字段。**任何「向后兼容」的读取都必须容错。**

### 12. 常量定义在 `__main__` 里，import 时不存在

`if __name__ == "__main__":` 块的变量**只在脚本模式**下定义。
模块级函数（`write_node`）和 import 方（`mcp/mcp_server.py`）都用不到。
**跨作用域共享的常量放模块级。**

### 13. 破坏性工具默认只预览

`fix_bom.py` 不带 `--apply` 只打印；目标值已存在时跳过并警告。
**让人先看一眼，比事后恢复便宜得多。**

### 14. 并行累积的字段没法原地重置，只能换个地方重开

`findings` 用 `Annotated[list, add]` 是因为 `fan_out` 并行派发、必须靠累加器合并；
所以「重跑前清空 `findings`」这条路根本不通（显式传 `[]` 会被 `add` 上旧数据）。

修法不是「清理」，而是**换一个干净的 thread_id 重开**（`pick_thread_id()`）。
**当一个容器天生只能加、不能减时，正确的做法是换一个容器，而不是想办法把它倒空。**
