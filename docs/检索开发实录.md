## 一、项目概览

### 目标

调研项目里有三段代码**共用同一个检索层**：

```
调研 Agent 查资料   ─┐
记忆库查历史会话     ─┼─→  BGE 向量检索 + cross-encoder 精排  →  research_docs
MCP 知识库服务       ─┘
```

**它好一分，三个项目一起好一分。** 但它一直是个黑盒：出了问题只知道「查不到」，不知道该改哪里。

### 起点：两个说不清的问题

| 问题 | 症状 |
|---|---|
| 分不清「真没有」还是「措辞没对上」 | 同样的阈值下，有的查询返回空、有的返回一堆不相关的，看不出规律 |
| 调参没有方向感 | 阈值、模型、prompt 都试过，改完只能凭感觉判断好坏 |

第二个的原因是：**一直没造出一把尺子。**

### 最终交付

| 类别 | 内容 |
|---|---|
| **尺子** | 训练集 19 条 + 留出集 14 条，人工标注标准答案 |
| **工具** | 逐级拆解 / 评测 / 失败诊断 / 评测集体检 / 成本测量 / 召回隔离 / 混合检索实验台 / BM25 分数拆解 |
| **基线数字** | 召回 0.91 · 精确 0.76 · MRR 0.95 · 拒答 7/8 |
| **一次落地** | MCP 服务的 `smart_query` 默认值 `False` → `True`（附实测依据） |
| **混合检索** | 从零手写 BM25 + 中文 token 化 + 停用词 + RRF；候选池召回 85.71% → **100%**（预算 k=3） |
| **接进链路** | `_retrieve` 改成「向量 ∪ BM25」混合粗筛（默认开）。⚠️ **但最终指标 0/19 变化** —— 瓶颈在精排层，不在召回层（第 11 课） |
| **阈值标定** | `RERANK_THRESHOLD` 0.3 → **0.9**（本语料标定）：精确 **0.76 → 0.91**、拒答 **7/8 → 8/8**，召回/MRR 不动。⚠️ 换语料必须重标（第 13 课） |

### 技术栈

| 组件 | 用什么 |
|---|---|
| 嵌入（粗筛） | `BAAI/bge-small-zh-v1.5`，512 维，`normalize_embeddings=True` |
| 精排 | `BAAI/bge-reranker-base`（CrossEncoder） |
| 稀疏检索 | **手写 BM25**（不依赖任何库）+ 汉字 bigram token 化 + 53 字停用词表 |
| 融合 | **手写 RRF**（Reciprocal Rank Fusion） |
| 框架 | `sentence-transformers 6.1.0` |
| 语料 | `research_docs/sample_ai_agents.txt`，**7 段** |

## 二、背景知识：检索是怎么工作的

### 2.1 六个环节

```
research_docs/*.txt
   ↓ ① 切块：按 "\n\n" 切段落，丢掉 ≤20 字的
7 个 chunk
   ↓ ② 编码：bge-small-zh-v1.5
embeddings（7 × 512）

查询进来 →
   ↓ ③ 编码成向量
   ↓ ④ 相似度 = embeddings @ qv          ← 粗筛（bi-encoder）
top coarse_k = 20
   ↓ ⑤ 精排：bge-reranker-base           ← cross-encoder 逐条重打分
   ↓ ⑥ 过滤 rr_scores < 0.3，最多取 max_k = 5
结果
```

**六个环节，每一环都可能出问题 —— 而它们出的问题看起来一模一样，都叫「查不到」。**

> **这就是「调参没有方向感」的根源**：你只有一个观测点（最后的输出），中间有六级。

**顺带解释了为什么正好是 7 段**：文件第 1 行的标题「大语言模型 Agent 的主流架构」只有 16 个字，被 `len(para) > 20` 这个过滤条件挡掉了。

### 2.2 为什么必须分开量

「检索效果不好」其实是几种**完全不同的病**，药也完全不同：

| 症状 | 病因 | 该动哪个零件 |
|---|---|---|
| 该找到的没找到 | 表示 / 召回问题 | 查询改写、混合检索 |
| 找到的排太后面 | 排序问题 | 精排模型、融合策略 |
| 返回一堆不相关的 | 判定问题 | 阈值、判定逻辑 |

**混在一个数字里看，永远不知道该改哪。**

## 三、开发过程（13 课）

### 第 1 课：拆开检索机

**先做的事不是修，是看。** 写 `anatomy.py`，把一个查询在**每一级**的分数都打出来。

#### 发现 1：向量粗筛是**空转**的

```python
coarse_k = 20                                    # main.py:115 默认值
idx = scores.argsort()[::-1][:coarse_k]          # 7 条里取 top-20 = 全部
candidates = [chunks[i] for i in idx]
rr_scores = reranker.predict(pairs)              # 对全部 7 条打分
order = rr_scores.argsort()[::-1]                # ← 按精排分重新排
```

**库里只有 7 段，粗筛保留 20 个** → `[:20]` 等于全部。而后面 `order` 是按 `rr_scores` 重排的，**向量分的排序用都没用上**。

`anatomy.py` 里的验证：

```
_retrieve 取到：['ReAct 架构...', 'Plan-and-Execu...']
纯精排   取到：['ReAct 架构...', 'Plan-and-Execu...']
两者完全相同：True
```

> **结论：当前检索 100% 由 cross-encoder 决定。**
> 你以为在开一台两级检索机，实际上只有一个零件在干活。

（注意：向量层**不是不行** —— 它把正确段落排在了第一，向量分 `0.7490` vs 第二名 `0.6035`。它是**没接上**。）

#### 发现 2：精排分是**概率**，不是 logits

我原本预测 `CrossEncoder.predict()` 返回原始 logits（会看到负数）。**这个预测错了。**

查了源码（`sentence_transformers 6.1.0`，`cross_encoder/model.py:425`）：

```python
    def get_default_activation_fn(self):
        if self.num_labels == 1:
            return nn.Sigmoid()
```

reranker 就是 `num_labels = 1`，所以**默认已经套了 Sigmoid** —— 分值在 `[0, 1]`，是概率。

> **教训**：「CrossEncoder 返回 logits」这个说法流传很广，但**这个默认值在版本历史上变过**。
> 属于那类「会随版本变、又不会报错」的默认值。

#### 发现 3：精排分是**双峰饱和**的

```
chunk[0] +0.9995   ← 正确（ReAct）
chunk[1] +0.9990   ← Plan-and-Execute
chunk[2] +0.0689
chunk[6] +0.0000
chunk[4] +0.0001
chunk[3] +0.0000
chunk[5] +0.0000
```

分数**全挤在两头**，中间是空的。把概率反推回 logit 就清楚了：

| 概率 | 反推的 logit `ln(p/(1-p))` |
|---|---|
| 0.9995 | **+7.6** |
| 0.9990 | **+6.9** |
| 0.0689 | −2.6 |
| 0.0000 | < −9.9 |

**两个后果**：

1. **阈值 `0.3` 在这份数据上「怎么定都一样」** —— 从 0.1 到 0.9 之间任何值，结果完全相同。**它从来没被真正考验过。**
2. **在饱和区，概率空间几乎没有分辨率** —— chunk[0] 和 chunk[1] 在 logit 空间差 **0.7**，取完 Sigmoid 后只差 **0.0005**。所以「用 top1 和 top2 的分差判断这次检索可不可信」这条路，在饱和区会失真。

#### 发现 4：「相关」≠「能作答」⚠️【这个结论后来被推翻了】

查询是 **「ReAct 架构的优缺点」**，而**讲 Plan-and-Execute 的段落拿到了 0.9990**，几乎和正确答案（0.9995）并列。

**当时的解释（错）**：

> ~~cross-encoder 判的是「这段文本和这个查询相关吗」，不是「这段文本能回答这个问题吗」。~~
> ~~两个 chunk 都在讲「Agent 架构」这个主题，所以对 reranker 来说都算相关。~~

**为什么错**：`chunk[1]` 的正文里有「**相比 ReAct 的「边想边做」**」—— 它**提到了 ReAct 并做了对比**。所以它拿 0.99 不是「主题相关」，而是**它确实能对「ReAct 的优缺点」贡献内容**（提供对比视角）。

**正确的解释**见[第 12 课](#第-12-课精排到底在判什么用扰动实验打开黑盒)：

> **cross-encoder 判的就是「这一段能不能回答这个查询」，而且判得很准。**

**这个错误还产生了连锁影响**：第 2 课那条标注纪律「`gold` 的语义是能回答，不是相关」是**对的**，但当时给的理由是错的（见下）。

**教训**：一个「看起来合理」的机制解释，会被后来的数据推翻。**当时写下它时没有做能证伪的实验** —— 因为诊断脚本只看了「分数是多少」，没看「分数随什么变化」。

### 第 2 课：建尺子

#### 三条标注纪律

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **人工标注，不许让 LLM 判分** | 7 段语料成本极低；用 LLM 判分 = 用另一个不可靠的东西衡量不可靠的东西 |
| 2 | **`gold` 的语义是「能回答」，不是「相关」** | 「相关」太宽（同域邻居都算），会把尺子泡松 |
| 3 | **不许先看检索结果再标注** | 否则标准答案会被**被测系统**带偏，你测的就成了「它和自己一致吗」 |

#### 五类查询

| 类型 | 条数 | 作用 |
|---|---|---|
| 直接 | 4 | 用文档里的原词 |
| 换词 | 4 | 意思一样，但不出现文档里的关键词 |
| 多概念 | 3 | 需要不止一段拼起来 |
| **近似无答案** | **6** | **主题相关，但问的细节库里没有** |
| 无关 | 2 | 完全不相干 |

#### ⭐ 为什么「近似无答案」必须是**最多**的一类

如果标注的查询全是「库里能回答的」，那测的只是：**找得到的时候能不能找到**。

而真正的痛点完全没被测到：**找不到的时候，系统会不会硬答。**

**这类查询的特征**：主题词一定命中（ReAct / Langfuse / 向量数据库……），所以向量分和精排分都会**很高**，但正确答案是**拒答**。

**七条现成的来源**（拿着每一段问「哪些细节没写」）：

| 库里提到的 | 库里**没**说的 | 可以出的查询 |
|---|---|---|
| [5] Langfuse、LangSmith | 哪个更好、多少钱 | 「Langfuse 和 LangSmith 哪个便宜」 |
| [4] 长期记忆用向量数据库 | 用哪个库、怎么选 | 「长期记忆该选 Milvus 还是 Chroma」 |
| [4] 短期记忆受上下文窗口限制 | 窗口到底多大 | 「上下文窗口最大是多少 token」 |
| [0] ReAct 的优缺点 | 提出年份、论文 | 「ReAct 是哪一年提出的」 |
| [2] 四种协作模式的名字 | 每种怎么实现 | 「Debate 模式具体怎么落地」 |
| [6] LLM 作为裁判 | 它自己准不准、有没有偏见 | 「LLM 当裁判会不会有偏见」 |

#### ⚠️ 然后我犯了一个典型错误

第一次提交的评测集里，**8 条 `gold` 全是 `[0]`** —— 从模板复制 `query` 时忘了改 `gold`。

写了个「评测集体检」工具（`check_eval_set.py`），用**分布**一眼抓出来：

```
chunk[0]   11 次  ███████████
chunk[1]    3 次  ███
chunk[2]    0 次
chunk[3]    0 次
chunk[4]    0 次
chunk[5]    0 次
chunk[6]    0 次
```

**7 段语料里有 5 段从来没被考过。**

**这个错误不报错。** 而且后果最恶劣：

| | |
|---|---|
| `gold` 里 `chunk[0]` 出现 11 次 | 系统也经常返回 `chunk[0]`（它是 ReAct 段，向量分最高） |
| → Recall 看起来很高 | → **评测显示「检索效果不错」** |

> **一把永远显示及格的尺子。**

改正之后：7 段全覆盖，分布均匀，「应该拒答」的占比从 31% 升到 **42%**。

### 第 3 课：量基线

#### 第一版指标漏了一样东西

第一版只量了**召回 / MRR / 拒答**。结果：

```
类型             条数   Recall@5     MRR       拒答正确
直接              4       1.00    1.00          —
换词              4       1.00    0.88          —
多概念             3       0.67    1.00          —
------------------------------------------------------------
```

**看起来很好** —— 直到把逐条结果摊开：

| 查询 | 取到 | gold | 返回段数 | 其中相关 | **精确率** |
|---|---|---|---|---|---|
| ReAct 架构的优缺点 | `[0, 1]` | `[0]` | 2 | 1 | **0.50** |
| Plan-and-Execute 架构的优缺点 | `[1, 2, 0]` | `[1]` | 3 | 1 | **0.33** |
| 多 Agent 架构 | `[2, 0]` | `[2]` | 2 | 1 | **0.50** |
| Agent 评测 | `[6, 5]` | `[6]` | 2 | 1 | **0.50** |

**`Recall@5 = 1.00` 让人以为「检索很好」，实际上返回的东西一半以上是多余的。**

补上精确率之后的完整基线：

```
类型             条数      召回      精确     MRR       拒答正确
直接              4    1.00    0.46    1.00          —
换词              4    1.00    0.88    0.88          —
多概念             3    0.67    1.00    1.00          —
近似无答案           6       —       —       —        5/6
无关              2       —       —       —        2/2
------------------------------------------------------------
总体             19    0.91    0.76    0.95        7/8
```

#### ⭐ 而 `Recall@5` 在这个语料上本来就是个**哑指标**

库只有 7 段，`coarse_k = 20` 取全部，**候选池就是全集**。唯一的门是阈值 —— 所以**只要过了 0.3 就一定被返回，召回几乎不可能低**。

`直接` / `换词` 两类 `Recall@5 = 1.00` 是**结构性饱和**，不是「检索效果好」。

> **选了一个测不出差别的指标。**

#### 以及「多返回的那一段到底是什么」⚠️【当时的解释后来被推翻了】

它没有表现为「该拒答的却高高兴兴返回」（那个预测错了，见专题 4），而是**精确率**：

```
查询：ReAct 架构的优缺点
gold = [0]          ← 只有这一段【能完整回答】
返回 [0, 1]
精确 = 0.50
```

**当时的解释（错）**：`chunk[1]` 是「相关，但不是答案」的噪音。

**正确的解释**见[第 12 课](#第-12-课精排到底在判什么用扰动实验打开黑盒)：`chunk[1]` 的正文里**提到了 ReAct 并做了对比**，所以它**对回答确有贡献**。

⇒ **精确率 0.46 可能不是「系统的问题」，而是「`gold` 标得太窄」** —— 这是一个还没验证完的假设（见第 12 课末尾）。

#### 三个失败案例

| 查询 | gold | 取到 | 问题 |
|---|---|---|---|
| 多 Agent 协作和 RAG 有什么不同 | `[2, 3]` | `[2]` | **chunk[3] RAG 被阈值砍了** |
| Agent 的记忆机制和 RAG 有什么不同 | `[3, 4]` | `[4]` | **chunk[3] RAG 又被砍了** |
| Langfuse 和 LangSmith 哪个便宜 | `[]` | 1 段 | 唯一一个「该拒答却答了」 |

#### 一个矛盾

| 问题 | 说明什么 | 想怎么修 |
|---|---|---|
| 「直接」精确率只有 0.46 | 阈值**太松** | **调高**阈值 |
| 「多概念」漏了 2 条 | 阈值**太紧** | **调低**阈值 |

**同一个旋钮，两个方向的需求。**

—— 但第 4 课证明，比这更糟。

### 第 4 课：逐级诊断

**不猜，把每条失败查询的每一级分数打出来。** `diagnose.py`：

```
查询：多 Agent 协作和 RAG 有什么不同     gold = [2, 3]

  [2] 多 Agent 协作      精排 +0.9881   ✅ 过  ★
  [3] RAG 检索增强生成    精排 +0.0073   ❌ 被砍 ★
  其余 5 段              精排 < 0.009

查询：Agent 的记忆机制和 RAG 有什么不同    gold = [3, 4]

  [4] 记忆机制           精排 +0.9908   ✅ 过  ★
  [3] RAG               精排 +0.0326   ❌ 被砍 ★
  其余 5 段              精排 < 0.013

查询：Langfuse 和 LangSmith 哪个便宜    gold = []
  [5] Agent 的可观测性    精排 +0.3093   ✅ 过  ← 刚超过 0.3
  其余 6 段              精排 +0.0000
```

#### 死因完全不同

| 案例 | gold 的精排分 | 真正死因 |
|---|---|---|
| 多 Agent 协作和 RAG | chunk[3] = **0.0073** | **查询需要拆开** |
| 记忆机制和 RAG | chunk[3] = **0.0326** | 同上 |
| Langfuse 哪个便宜 | chunk[5] = **0.3093**（刚过线） | 判定边界太紧 |

#### ⭐⭐ 前两条的真相：**查询形式**

**同一个模式，两次**：查询是「**A 和 B 有什么不同**」这种**比较型问题**，reranker 把 **A 段给到 0.99**，把 **B 段给到 0.00~0.03**。

因为：

> **「A 和 B 有什么不同」这个整句，chunk[2] 只答得了 A 那一半，chunk[3] 只答得了 B 那一半 —— 严格说两个都答不了整句。**
> reranker 给了 A 段 0.99，因为它是查询里的**第一个主体**、更「像」答案。

**所以这不是排序问题，也不是阈值问题 —— 是「这个查询本身就不该整句拿去检索」。**

#### ⚠️ 顺便证明「调阈值」是一条死路

要「保留 chunk[0]、砍掉 chunk[1]」，阈值必须落在这两个数之间：

```
chunk[0]（正确）  0.9995
chunk[1]（邻居）  0.9990
                  ↑ 阈值得卡在 0.9990 ~ 0.9995 之间，区间宽 0.0005
```

而 chunk[3] 被砍是因为它低于 **0.3**。

**一个旋钮要同时做到「卡到小数点后四位」和「放到 0.3 以下」—— 不可能。**

> **分数饱和之后，阈值就失去了分辨能力。** 这不是「调得不够好」，是**这个零件在判定层上不解决问题**。

### 第 5 课：对照实验 —— 查询分解

#### 发现系统里本来就有这个功能

`main.py:147`：

```python
def search(query, ...):
    """【多查询】分解 → 逐个子查询检索 → 合并去重

    目的：解决「复合问题」——一个问题含多个概念时，
          单个查询向量会被稀释，导致某些概念检索不到。
    """
    sub_queries = decompose(query) if use_decompose else [query]
```

**它的 docstring 一字不差地描述了刚诊断出的症状。** 而 MCP 服务调它时 `smart_query` **默认是 `False`**。

#### 对照实验设计

**只改一个变量**：有没有查询分解。

```python
RETRIEVERS = [
    ("单查询（现在的默认）", lambda q: R._retrieve(q)),
    ("带查询分解（全开）",   lambda q: R.search(q, use_decompose=True)),
]
```

#### 结果（训练集）

| 指标 | 单查询 | 带分解 | 变化 |
|---|---|---|---|
| 召回 | 0.91 | **1.00** | +0.09 ✅ |
| MRR | 0.95 | **1.00** | +0.05 ✅ |
| 拒答 | 7/8 | **8/8** | +1 ✅ |
| 精确 | 0.76 | 0.76 | 持平 |

#### 它比预测的**多治了一条**

预测会救回 2 条多概念。**实际救回 3 条** —— 连「Langfuse 哪个便宜」也一起治好了：

```
[多概念]   多 Agent 协作和 RAG    [2]  →  [2, 3]   ✅
[多概念]   记忆机制和 RAG         [4]  →  [4, 3]   ✅
[近似无答案] Langfuse 哪个便宜     [5]  →  空       ✅ 正确拒答
```

**为什么第三条也被治好了？** 因为「Langfuse 和 LangSmith 哪个便宜」**也是一个复合问题**（两个工具名）。拆成两个子查询之后，**两个都答不了 → 合并起来是空的 → 正确拒答。**

> **我之前的诊断错了一半**：我把它归成「阈值边界太紧」，**那只是表象；病根和那两条多概念是同一类。**

#### 「改善」和「变坏」都能精确归因

11 条有答案查询的精确率之和：**8.33 → 7.83**。而只有**一条**查询的精确率变了（`如何追踪Agent内部每一步` → 多带了 `chunk[0]`）：

```
0.50 ÷ 11 = 0.045 ≈ 0.05    ← 和总体差值完全对应
```

**不是「感觉好点了」，是「这一条好了、那一条坏了，别的都没动」。**

### 第 6 课：留出集 —— 判决

#### 为什么要它

> **我们用这 19 条题设计了规则，又用这 19 条题给规则打分。**
> **这就像自己出题、自己考、自己打分。**

#### 三条纪律

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | 写的时候不参考评测结果 | 不能「挑几条规则一定会失败的」 |
| 2 | **跑完不回头改规则再测同一批** | 否则留出集就变成了训练集 |
| 3 | **结果不好就承认规则不行** | 而不是「那我再加几个关键词」 |

**第 2、3 条是留出集的全部意义。一个可以反复调整的留出集，等于没有留出集。**

#### 「智能分解」的想法

`decompose` 对**每条**查询都调一次 LLM（即使结果是「原样返回」）。所以用一条**文字规则**预判像不像复合问题，可疑的才调 LLM：

```python
COMPOUND_MARKERS = ("和", "与", "、", "以及", "还有", "对比", "区别",
                    "有什么不同", "哪个", "分别")

def looks_compound(query):
    return any(m in query for m in COMPOUND_MARKERS)
```

**为什么用文字规则而不是检索分数**：诊断数据显示，复合查询在精排分上也是「一个段落一枝独秀」（0.9881 vs 其余 <0.01），**和单概念查询长得一模一样** —— 分数判别不了。

#### 留出集的设计：四类对抗样本

| `kind` | 特征 | 期望 |
|---|---|---|
| 对抗-真漏判 | 需要 2 段以上，但文字里**没有**并列标记 | 规则会漏 → 质量下降 |
| 对抗-假漏判 | 看着像复合，其实答案**就在同一段** | 规则不命中**才是对的** |
| 对抗-命中 | 需要 2 段，且文字里**有**并列标记 | 规则应该命中 |
| 对抗-误判 | 就是单概念，但文字里**恰好有**并列标记 | 规则白花一次 LLM |

**「假漏判」这一类是最值钱的** —— 它说明：

> **「文字上像复合问题」和「需要拆开检索」不是一回事。**

（例子：「Agent 的两个评测方法各有什么优势」→ 两种方法**都写在 chunk[6] 里**，拆开反而可能丢。）

#### 判决：规则**没有通过**

```
策略                        召回      精确    MRR        拒答
单查询（现在的默认）              0.86    0.91    0.93       0/0
带查询分解（全开）               1.00    0.95    1.00       0/0
智能分解（规则预筛）              0.93    0.91    1.00       0/0

智能分解的 LLM 调用：4/14 条查询（29%）
```

**两条「真漏判」全军覆没**（召回 0.50 vs 全开 1.00），而且「对抗-命中」里有一条特别戏剧：

```
RAG 与 记忆机制 对照有什么优势    gold=[3,4]
   单查询：取到[]       召回 0.00   ← 完全失败，两段都被阈值砍了
   全开：  取到[3, 4]   召回 1.00
```

#### ⭐⭐ 训练集和留出集给出了**不同**的答案

| 数据集 | 单查询召回 | 全开召回 | 智能召回 | 结论 |
|---|---|---|---|---|
| **训练集**（19 条） | 0.91 | 1.00 | **1.00** | 「智能和全开**一样好**，成本只要 21%」 |
| **留出集**（14 条） | 0.86 | 1.00 | **0.93** | 「智能**明显差一截**」 |

> **在训练集上，智能分解和全开一模一样。在留出集上，差了 0.07。**
> **如果没有留出集，我们会带着一个错结论去改生产代码。**

**这就是留出集存在的全部理由 —— 它抓到了训练集看不见的差距。**

#### 一个设计疏漏（要记下来）

留出集的 `拒答` 一列是 **0/0** —— **一条「应该拒答」的查询都没有。**

是我设计类别时漏了：只顾着测「拆不拆」，忘了测「该不该答」。**所以这份留出集验不了「拒答」这个能力。**

不是坏结果（留出集本来就该小、该聚焦），但**要知道它的盲区在哪** —— 否则你会以为「拒答没问题」，其实只是**没测**。

### 第 7 课：落地 —— 并且看清失败的原因

#### 先量成本

写 `measure_decompose.py`，对留出集 14 条各跑一次：

```
共 14 次调用
  平均     0.70s
  中位数   0.71s
  最慢     0.99s

  拆出多个子查询的：9/14 条（64%）
```

#### C 的答案：**不需要优化**

**平均 0.7 秒，换来留出集召回 0.86 → 1.00。**

> **优化一个 0.7 秒的调用，是过早优化。**

#### ⭐⭐ 但这一跑真正的收获在输出里

**这是整个过程中第一次看到 `decompose` 的输出。**

##### 发现 1：它实际拆了 **9/14**，而规则只预测了 **4/14**

规则命中率 29%，实际需要处理的 64%。

##### 发现 2：它把「优缺点」拆成了「优点」+「缺点」

```
记忆机制的优缺点是什么
    └─ 记忆机制的优点
    └─ 记忆机制的缺点
```

**「优缺点」是一个词，里面藏着两个含义。** 真实用户经常这么问（「有什么利弊」「优劣」）。

**任何关键词规则都不可能捕捉这个** —— 它不是并列结构，是**词内部的两个意思**。

##### 发现 3：它不只是「拆」，还会**改写**

```
多 Agent 协作的机制是什么
    └─ 多 Agent 协作机制          ← 不是原查询！

RAG 的优势是什么
    └─ RAG 的优势                 ← 去掉了「是什么」
```

**这解释了那条最奇怪的样本**：

```
[真实] 多 Agent 协作的机制是什么    gold=[2]
   单查询：取到[2, 4]   精确 0.50
   全开：  取到[2]      精确 1.00
```

查询被改写成「多 Agent 协作机制」之后**更聚焦了，邻居 chunk[4] 不再混进来** —— 精确率 0.50 → 1.00。

**它救的不是「漏」，是「多」。**

#### 所以规则为什么必然失败 —— 有两条铁证

| `decompose` 实际在做什么 | 文字规则能做到吗 |
|---|---|
| 按连接词拆分（「A 和 B」） | ✅ 能 |
| **把「优缺点」拆成「优点」+「缺点」** | ❌ **做不到** |
| **把「…的机制是什么」改写成「…机制」** | ❌ **做不到** |

**规则不是「关键词不够全」，是这个任务本身超出了规则的能力范围。**

上一课靠留出集**发现**了规则不行；这一课**看清了为什么不行**。两件事合起来才完整 —— **只知道「不行」，你下次会想「那我再加几个词试试」；知道「为什么不行」，你才不会再去撞这堵墙。**

#### 落地

`mcp/mcp_server.py`，`smart_query` 默认值 `False` → `True`，并把依据写进代码注释：

```python
    # ⚠️ smart_query 默认改成 True 的依据（留出集 14 条实测）：
    #      关闭：召回 0.86  精确 0.91
    #      开启：召回 1.00  精确 0.95
    #    代价：每次检索多约 0.7 秒（一次 LLM 调用）。
    #    这个交换比很划算 —— 而且「查询分解」不只是拆复合问题，
    #    它还会【改写查询】（例如「…的机制是什么」→「…机制」），
    #    这一层收益靠任何关键词规则都拿不到（实测过，规则版在留出集上失败）。
    smart_query: bool = True,
```

### 第 8 课：把「召回」从链路里隔离出来量

#### 为什么要隔离

现在 gold 没找到，可能是三处任何一处的问题：

```
召回层（压根没进候选） → 精排层（进了但排错） → 阈值（排对了但被砍）
```

`recall_lab.py` 把后两处**拿掉**，只问一个问题：

> **「假设精排和阈值都是完美的，光靠召回能不能把 gold 拿进来？」**

#### ⚠️ 但必须看 k 小的那一头

库里只有 7 段。**k=7 时候选池就是全集，召回必然 100%** —— 那不是「召回好」，是「召回没在筛」。

有信息量的是 k=1、k=2。

#### 结果：向量召回曲线

```
 top-k       召回率
     1    71.43%   ████████████████████████
     2    85.71%   █████████████████████████████
     3    85.71%   █████████████████████████████   ← 第 3 名一个 gold 都没带来
     4   100.00%
     5..7 100.00%

类型         条数    k=1      k=3
直接          4  100.00%  100.00%
换词          4   75.00%  100.00%
多概念         3   50.00%   66.67%
```

**三个发现**：

| # | 发现 |
|---|---|
| 1 | **向量第一名只有 71.43%** —— 「向量排序很准」这个印象是错的，只是候选池太大盖住了问题 |
| 2 | **k=2 → k=3 完全没涨** —— 第 3 名一个 gold 都没带来；漏的要等到 k=4 才齐 |
| 3 | **多概念在 k=3 只有 66.67%** —— 3 条查询共 6 个 gold，只有 4 个进了前三 |

#### ⭐ 这才让「混合检索」有了用武之地

```
现在：coarse_k = 20，库里 7 段   →  候选池 = 全集  →  召回 100%（假象，因为没在筛）
如果：coarse_k = 3                →  召回掉到 85.71%，多概念只剩 66.67%
```

**召回层确实有空间 —— 只是在 7 段语料上被「候选池=全集」掩盖了。**

**而且这直接推出结论**：往召回层加 BM25 之前，**必须先把预算压下来**，否则加了也是全集，什么都测不出来。

### 第 9 课：写一个 BM25，然后找到它的病根

#### 零件和实验分开

第一版把演示代码写在了 `hybrid_lab.py` 的模块顶层 —— 结果它**没法被 import**（一 import 就整个实验跑起来）。拆成：

| 文件 | 职责 |
|---|---|
| `bm25.py` | **零件**：`tokenize` / `BM25` / `rrf`（只定义，不跑） |
| `hybrid_lab.py` | **实验**：比较几种候选来源 |
| `bm25_dig.py` | **诊断**：把分数拆到 token 级别 |

#### 中文的 token 问题

BM25 需要「词」，而中文没有空格。三个 BM25 库和 `jieba` **一个都没装** —— 正好，手写。

```
英文/数字连续串 → 整词保留         'ReAct' → ['react']
单个汉字        → 单字 + 相邻 bigram   '检索增强' → ['检','索','增','强','检索','索增','增强']
```

**为什么不能对中文直接做 bigram、对英文也做**：`'ReAct'` 做 bigram 会变成 `'re','ea','ac','ct'` —— 语义全碎。

> **⭐ 顺带说明：「什么算一个 token」是可以自己设计的**，不是天经地义的。换一种切法，检索结果就会不一样。

#### 第一次对比：BM25 竟然打赢了向量

```
语料 7 段   候选预算 k = 3

候选来源         召回率
向量          85.71%   (12/14)
BM25        92.86%   (13/14)
融合          92.86%   (13/14)
```

**一个 30 行手写的 BM25，打赢了 512 维的 BGE 向量。**

原因和「向量分数地板」是同一个现象的两面：

| | 向量 | BM25 |
|---|---|---|
| 7 段语料都讲 Agent → 语义空间里**互相很近** | 向量分全挤在 0.42~0.46，**分不开** | — |
| 「RAG」这类**精确词** | 被语义平均掉了 | **只在某几段出现 → 区分度极高** |

**语料越同域，向量的优势越小、BM25 的优势越大。**

#### ⚠️ 但融合**一点都没提升**

```
向量 12/14    BM25 13/14    融合 13/14    ← 和 BM25 一模一样
```

**RRF 是「平等对待两路信号」的，它不知道哪一路更准。**

```
「Plan-and-Execute 架构的优缺点」
   BM25   [0, 1, 2]   ← 正确的 1 排第 2
   向量   [1, 2, 0]   ← 正确的 1 排第 1
   融合   [1, 0, 2]   ← 向量的第 1 名把 BM25 的第 1 名挤到了第 2
```

> **融合不会自动变好。** 它是「平均」，而平均一个好东西和一个坏东西，得到的是中间值。

#### 一个具体的、还没解释的线索

```
gold=[2, 3]  多 Agent 协作和 RAG 有什么不同
   向量   ⚠️ [2, 6, 5]    漏了 3
   BM25  ✅ [2, 0, 3]    捞到了 ✅

gold=[3, 4]  Agent 的记忆机制和 RAG 有什么不同
   向量   ⚠️ [4, 5, 2]    漏了 3
   BM25  ⚠️ [4, 0, 1]    漏了 3
   融合   ⚠️ [4, 5, 0]    漏了 3
```

**同一个 chunk[3]，一条查询 BM25 能捞、另一条三种方式都捞不到。** 差在哪？

#### 把分数拆到 token 级别

`bm25_dig.py`。BM25 的分数是**可加的**（每个查询 token 的贡献之和），所以能逐个拆开 —— **这是 BM25 相对向量的一个真实优势**：向量相似度是一个整体值，你没法说「这个 0.42 里，'RAG' 贡献了多少」。

```
查询：Agent 的记忆机制和 RAG 有什么不同

③ chunk[3] 的 BM25 分数（总分 3.389）
   token      IDF    本段出现   贡献
   rag       1.674      3      2.761    ← 81% 的分数来自这一个词
   → 命中 3/22 个 token

④ chunk[0] 的分数拆解（总分 5.338）
   ⚠️ 这一段【不在 gold 里】，BM25 却把它排在第 2 名
   token      IDF    本段出现   贡献
   agent     0.375      1      0.364
   的         0.065      2      0.090
   什         1.674      1      1.628   ←
   什么       1.674      1      1.628   ←
   么         1.674      1      1.628   ←
```

**chunk[0] 一共 5.338 分，其中 4.884 分（91.5%）来自「什」「什么」「么」。**

#### ⭐⭐ 根因：疑问句的功能词被当成了实词

这三个 token 来自查询里的 **「有什么不同」**。它们为什么命中 chunk[0]？

因为 chunk[0] 的正文里有：

> 「模型先思考当前应该做**什么**」

**「应该做什么」里的「什么」，和「有什么不同」里的「什么」，被当成了同一个词。** 而「什么」在语料里很罕见 → **IDF = 1.674（高分词）** → 贡献巨大。

完整链条：

```
查询里有「有什么不同」
   ↓ bigram 切词
token 里混进「什」「什么」「么」「不同」「有」
   ↓ 它们在语料里几乎只出现在【陈述句】里
chunk[0] 的「应该做什么」命中 → 白拿 4.884 分
   ↓
chunk[0]（讲 ReAct 的，和查询无关）排到第 2 名
   ↓
把真正该排前面的 chunk[3] 挤到第 5 名
```

**顺带暴露第二个问题**：`什`（单字）、`什么`（bigram）、`么`（单字）是**同一个「什么」的三种切法**，却**各得 1.628 分** —— 单字和 bigram 同时保留导致重复计分。

#### 修法：停用词表

`STOPWORDS`：53 个「单独出现时没有实义」的字（的了着过地得 / 和与及或 / 这是有在 / 什么怎如何 / 不同区别比较 / 就都也还而但为 …）。

**过滤规则（关键）**：

```
· 命中停用词的字【不单独成为 token】
· 而且【只要有一边是停用词，这个 bigram 也不生成】
  —— 否则「有什么不同」里的「什么」还是会冒出来
```

实测：

```
带停用词: ['agent', '记', '记忆', '忆', '忆机', '机', '机制', '制', 'rag']   ← 9 个，全是实词
不带    : ['agent', '的', '的记', ..., '什么', '么', '么不', '不', '不同', '同']  ← 22 个
```

**22 个 token 里 13 个是噪音，全清掉了。**

#### 结果：92.86% → 100%

```
候选来源            召回率
向量             85.71%
BM25           92.86%
BM25+停用词      100.00%    ← 唯一变量：53 个字的停用词表
融合             100.00%

类型         向量        BM25    BM25+停用词
直接     100.00%     100.00%     100.00%
换词     100.00%     100.00%     100.00%
多概念    66.67%      83.33%     100.00%
```

**而且那条「三种方式都漏」的查询被修好了**：

```
gold=[3, 4]  Agent 的记忆机制和 RAG 有什么不同
   向量        ⚠️ [4, 5, 2]
   BM25       ⚠️ [4, 0, 1]
   BM25+停用词  ✅ [4, 1, 3]    ← 3 进前三了
```

**这正是机制上预测的那条** —— chunk[0] 靠「什么」白拿 4.884 分被顶到第 2 名，去掉「什么」之后它掉下去了，chunk[3] 自然浮上来。

**诊断 → 假设 → 验证，闭环。**

### 第 10 课：预算曲线 —— RRF 值不值

#### 天花板效应

第 9 课最后一栏「融合 100%」和「BM25+停用词 100%」**打平** —— 但这是**天花板**，测不出融合有没有用。

而 RRF 的经典结论是：**候选预算越紧，融合的优势越大。**

所以把预算做成三档跑：

```
候选来源              k=1       k=2       k=3
向量               71.43%    85.71%    85.71%
BM25              71.43%    85.71%    92.86%
BM25+停用词         71.43%    92.86%   100.00%
融合               78.57%    85.71%   100.00%

⭐ 融合 vs 最好的单路：
   k=1   融合 78.57%   最好单路 71.43%    +7.14%   → 融合更好 ✅
   k=2   融合 85.71%   最好单路 92.86%    -7.14%   → 融合更差 ❌
   k=3   融合 100.00%  最好单路 100.00%   +0.00%   → 打平 ➖
```

#### ⭐ k=1：融合赢了，而且赢的方式正是教科书说的

**k=1 时四种方式的「单路」全都是 71.43%**，只有融合 78.57%。

```
gold=[1]  Plan-and-Execute 架构的优缺点
   向量 ✅ [1]       BM25 ❌ [0]       融合 ✅ [1]   ← 向量对、BM25 错

gold=[0]  怎么让模型一边思考一边调用工具
   向量 ❌ [1]       BM25 ✅ [0]       融合 ✅ [0]   ← BM25 对、向量错
```

按类型拆开，互补性一目了然：

```
类型      条数     向量      BM25   BM25+停用词    融合
直接       4   100.00%   75.00%     75.00%   100.00%   ← 向量强
换词       4    75.00%  100.00%    100.00%   100.00%   ← BM25 强
多概念      3    50.00%   50.00%     50.00%    50.00%
```

| 查询类型 | 谁强 | 为什么 |
|---|---|---|
| **直接**（用原文词） | **向量** | BM25 的词面匹配会被「优缺点在别处也出现」带偏 |
| **换词**（改写了说法） | **BM25** | 向量把语义模糊化了；BM25 抓不住同义，**但至少不误导** |

**而融合在两类上都是 100%** —— 它拿到了两路各自最强的那一面。

#### ⚠️ 但 k=2 时融合**反而更差** —— RRF 的代价

RRF 的公式是 `Σ 1/(60 + 名次)`，两路贡献**相加**。于是：

| 文档 | 向量名次 | BM25 名次 | RRF 分 |
|---|---|---|---|
| A | 1 | 5 | 1/61 + 1/65 = **0.0318** |
| B | 2 | 2 | 1/62 + 1/62 = **0.0323** ← B 赢 |

**B 在任何一路都不是第一名，但它「两路都还行」，于是在 RRF 里赢了。**

这是 RRF 的**设计意图**（共识优先），代价是：**某一路的强信号会被另一路的中等信号压过去。**

> **RRF 不是「白拿好处」的融合 —— 它在紧预算时帮你，在中预算时可能害你。**

#### 所以「该不该用 RRF」的答案是：取决于预算

| 你的预算 | 建议 | 理由 |
|---|---|---|
| **很紧**（k=1） | ✅ 用融合 | +7.14%，明确更好 |
| 中等（k=2） | ⚠️ 小心 | **这一档融合反而更差** |
| 宽松（k≥3） | ➖ 没必要 | 打平，还要多算一路 |

**这比「混合检索总是更好」有用得多** —— 而且它直接回答了最初的问题：

> 「往召回层加 BM25 值不值得？」
> **值得，但先看你的预算。** 如果你本来就给 20 个候选（像现在的 `coarse_k=20`），加了也白加。

#### ⚠️ 诚实边界：样本太小

**1 个 gold 的差异 = 7.14%**（总共只有 14 个 gold）。

| 结论 | 相当于 |
|---|---|
| 融合 > 单路（k=1） | **1 个 gold** |
| 向量 > BM25（直接类） | 4 条查询上差 **1 个 gold** |

| 说法 | 站得住吗 |
|---|---|
| 「融合在 k=1 下更好」 | ⚠️ 有机制支撑 + 数据一致，但样本太小，只能说「支持」 |
| 「直接类向量强、换词类 BM25 强」 | ⚠️ 同上 —— 但机制上说得通（稠密/稀疏的经典互补），可信度更高 |
| 「BM25+停用词把召回 92.86% → 100%」 | ✅ **有机制**（那 4.884 分来自「什么」），这条最硬 |

### 第 11 课：接进真实链路 —— 发现瓶颈不在这

#### 先做一个设计决策：并集，还是融合？

前 10 课的实验测的是「**按排名取前 k 个**」的召回率。但真实链路后面**还有精排**：

```
召回层 → 精排层 → 阈值
         ↑ 精排比任何融合方式都强
```

**所以召回层唯一的目标是「不丢」，排序交给精排就行。**

| 做法 | 候选数 | 会不会丢 |
|---|---|---|
| RRF 融合后取 top-k | k | **可能丢**（实测 k=2 时就丢过一个） |
| **向量 top-k ∪ BM25 top-k** | 最多 2k | **一定不丢**（并集必然包含任何单路的 top-k） |

**所以接进链路用并集，不用 RRF。**

> RRF 不是白研究了 —— 它回答的是一个具体问题：**「融合后直接取前 N 个」时它有用（k=1 时 +7.14%）；但下游有精排时，并集才是对的工具。**

#### 改法

```python
def _retrieve(query, max_k=5, min_score=RERANK_THRESHOLD, coarse_k=20,
              use_bm25=True):
    picked, seen = [], set()

    def take(i):
        i = int(i)
        if i not in seen:
            seen.add(i); picked.append(i)

    # 稠密：语义相似
    qv = model.encode(query, normalize_embeddings=True)
    vec_scores = embeddings @ qv
    for i in vec_scores.argsort()[::-1][:coarse_k]:
        take(i)

    # 稀疏：精确词匹配
    if use_bm25:
        for i in bm25.ranking(query)[:coarse_k]:
            take(i)

    candidates = [chunks[i] for i in picked]
    # …精排和阈值完全不变（顺序由精排决定，所以粗筛顺序无所谓）
```

#### 验证：同一把尺子，四个策略，**结果完全一样**

```
预算 20 · 纯向量（旧的默认）      0.91  0.76  0.95  7/8
预算 20 · 混合（∪BM25）        0.91  0.76  0.95  7/8
预算 3  · 纯向量               0.91  0.76  0.95  7/8
预算 3  · 混合（∪BM25）        0.91  0.76  0.95  7/8

共 0/19 条结果不同
```

**第一个原因预料之中**：`coarse_k = 20 > 7 段` → 候选池 = 全集 → 加什么都是全集。

**但预算 3 时也一模一样 —— 这才是意外。**

#### ⭐ 为什么预算 3 时也没变

拿那条追了三课的查询来对：

```
查询：多 Agent 协作和 RAG 有什么不同      gold = [2, 3]

预算 3 · 纯向量
   向量 top-3 = [2, 6, 5]     ← chunk[3] 【压根没进候选池】
   结果：只有 [2]             召回 0.50

预算 3 · 混合
   BM25 top-3 = [2, 0, 3]     ← chunk[3] 【进池了】✅
   并集 = {2, 6, 5, 0, 3}
   结果：还是只有 [2]          召回 0.50
```

**chunk[3] 确实被 BM25 捞进候选池了 —— 然后精排给了它 `0.0073`，被阈值 0.3 砍掉。**

> **两条路殊途同归：一条是「没进池」，一条是「进了池但精排判它不相关」。**

#### ⭐⭐ 所以瓶颈根本不在召回层

第 8~10 课把**候选池的召回**从 85.71% 提到 100% —— **那个提升是真实、可测的**。**但最终结果一条都没变。**

因为这是条**串联**链路：

```
召回层 → 精排层 → 阈值 → 结果
   ↑ 我们改的这里        ↑ 瓶颈在这里
```

> **串联系统的优化，只有在瓶颈上做才有效。改上游，下游一道门就把它挡住了。**

**这也呼应了专题 5 的第三层「量的对象」**：`hybrid_lab` 只看召回层，**它永远看不到这件事**。差点就拿着「召回 100%」去宣布胜利了。

#### 重新看三个失败案例的真正瓶颈

| 案例 | 召回层 | 精排层 | 阈值 | **真正瓶颈** |
|---|---|---|---|---|
| 多 Agent 协作和 RAG | ❌ 向量漏了 | chunk[3] = **0.0073** | 砍掉 | **精排** |
| 记忆机制和 RAG | ❌ 都漏 | chunk[3] = **0.0326** | 砍掉 | **精排** |
| Langfuse 哪个便宜 | ✅ 有 | chunk[5] = 0.3093 | 勉强过 | **判定** |

**为什么精排给 chunk[3] 0.0073？** 因为查询是「多 Agent 协作**和** RAG 有什么不同」—— 一个**复合问题**，而 chunk[3] 只答得了 RAG 那一半。**精排判「这一段不能回答这个问题」→ 接近 0。**

⭐ **第 4 课的诊断一开始就是对的**：复合问题的解法是**查询分解**，不是召回优化。

**而查询分解已经落地了**（MCP 的 `smart_query` 默认 `True`）—— **那才是治这个病的药。BM25 治的是另一个病，而这个病现在没犯。**

#### 那 BM25 该不该留？`coarse_k` 该不该改？

**BM25 留。** 三个理由：

| 理由 | 说明 |
|---|---|
| 成本近零 | 纯 Python 数词频，语料变动时才重建；检索时几毫秒 |
| 结构上已经对了 | `coarse_k = 20` 是按**未来语料规模**设的常数 —— 语料一旦超过 20 段，粗筛自动开始生效 |
| 它没做错 | 候选池召回 85.71% → 100% 是实测的，**只是当前瓶颈不在这** |

**`coarse_k = 20` 不改**：

- 它的意义是**控制精排成本**（cross-encoder 是 O(候选数) 的）
- 7 段时压紧它**没有任何收益**（精排 7 次 vs 4 次都是毫秒级）
- 1000 段时它才开始真正必要

> **为了「让 BM25 看得出效果」而压低 `coarse_k`，是纯粹的降级。**

#### 这一课真正的收获

| 表面上的结果 | 真正的收获 |
|---|---|
| BM25 接进链路了，但指标没动 | ⭐ **发现瓶颈在精排层，不在召回层** |
| 白干了吗？ | 没有 —— **如果没做这次真实链路评测，会带着「召回 100% = 系统变好了」的错结论去交付** |

> **优化了一个不是瓶颈的地方，测量会告诉你「没变」—— 而这比「看起来变好了」有用得多。**

**`hybrid_lab` 说「+14%」，真实链路说「+0%」。两个都是对的，但只有后者是决策依据。**

### 第 12 课：精排到底在判什么（用扰动实验打开黑盒）

#### 起点：一条反常的数据

第 4 课的诊断里有一条我们**没有认真解释**的数据：

```
查询：多 Agent 协作和 RAG 有什么不同      gold = [2, 3]

chunk[2] 多 Agent 协作      精排 +0.9881   ✅
chunk[3] RAG 检索增强生成    精排 +0.0073   ❌ ← ？
```

**查询里明明有「RAG」，段落也整段在讲 RAG —— 为什么只有 0.0073？**

而我们当时的解释（「它判相关不判能作答」）**和另一条数据是矛盾的**：

```
查询：ReAct 架构的优缺点
chunk[1] Plan-and-Execute   精排 +0.9990   ← 讲别的架构，却接近满分
```

**一个「不太相关的」拿 0.99，一个「就是讲这个的」拿 0.007。** 解释不通 —— 但当时没做能证伪的实验，就把这个解释写进了文档。

#### 怎么问一个黑盒

cross-encoder 的内部看不到，但可以**扰动输入看输出怎么动**：固定全部段落，只改查询的某一个方面。

| 试探 | 意图 |
|---|---|
| `多 Agent 协作和 RAG 有什么不同` | 原句 |
| **`RAG 和多 Agent 协作 有什么不同`** | **只调换两个主体的顺序** |
| `多 Agent 协作` / `RAG` | 各自单独出现 |
| `多 Agent 协作是什么` / `RAG 是什么` | 主体 + 疑问 |
| `多 Agent 协作 RAG` | 两个主体，**没有**疑问词 |
| `有什么不同` | 纯功能词 |

**⭐ 「只调换顺序」是决定性的**：如果换了顺序之后分数**互相交换**，说明模型在看**位置**而不是看语义。

#### 结果一：调换顺序 —— 分数**完全没变**

```
原句：多 Agent 协作和 RAG 有什么不同    →  chunk[2]=0.9881   chunk[3]=0.0073
调换：RAG 和多 Agent 协作 有什么不同    →  chunk[2]=0.9932   chunk[3]=0.0071
                                                   ↑ 没变              ↑ 没变
```

**不是位置偏差。假设被推翻。**

#### 结果二：真正的规律 —— 两个主体一出现，分数就崩

```
查询                                  chunk[2]   chunk[3]
─────────────────────────────────────────────────────────────
「RAG」（只留第二个主体）                  0.0004     0.9784   ← 满分
「RAG 是什么」                          0.0001     0.9605   ← 高分
─────────────────────────────────────────────────────────────
「多 Agent 协作」（只留第一个主体）          0.9999     0.0000
「多 Agent 协作和 RAG 有什么不同」          0.9881     0.0073   ← 崩了
「多 Agent 协作 RAG」（两个主体，无疑问词）    0.9960     0.0030   ← 也崩
─────────────────────────────────────────────────────────────
「有什么不同」（纯功能词）                  0.0192     0.0016
```

**「RAG」单独问 → 0.9784；带上另一个主体 → 0.0073。差 134 倍。**
**而且「有没有疑问词」不影响**（`多 Agent 协作 RAG` 一样崩）—— 所以不是句式问题，是**主体个数**问题。

#### ⭐⭐ 修正后的解释

**旧（错）**：

> ~~cross-encoder 判的是「这段文本和这个查询相关吗」，不是「这段文本能回答这个问题吗」。~~

**新（对）**：

> **它判的就是「这一段能不能回答这个查询」，而且判得很准。**

三个现象用同一个解释全部说通：

| 查询 | 段落 | 分数 | 为什么 |
|---|---|---|---|
| 「RAG」 | chunk[3] | **0.9784** | 单主体，这一段**就是答案** |
| 「RAG 是什么」 | chunk[3] | 0.9605 | 同上 |
| **「多 Agent 协作和 RAG 有什么不同」** | chunk[3] | **0.0073** | **关系型问题 —— 单段答不了「两者的不同」** |
| 「ReAct 架构的优缺点」 | chunk[1] | 0.9990 | chunk[1] **提到了 ReAct**（「相比 ReAct 的『边想边做』」）→ 对「优缺点」确有贡献 |

**关键在最后一行**：chunk[1] 拿 0.99 **不是**因为「它主题相关」，而是因为**它确实能对「ReAct 的优缺点」贡献内容**（提供了对比）。

**所以精排没有毛病，它是诚实的** —— 它说「**没有一段能回答这个复合问题**」。**这个判断是对的。**

**错的是检索架构**：**问一个复合问题，却期望单段来回答。**

#### ⭐⭐⭐ 于是整条逻辑链闭合了

这正好解释了**为什么查询分解有效**（第 5 课，那个结论本来只是「实测有效」）：

```
复合问题「A 和 B 有什么不同」
   ↓ 整句去检索
精排：没有一段同时覆盖 A 和 B → 全给接近 0 → 全被阈值砍   ❌
   ↓ 查询分解
子查询「A」 → 段落 A 得 0.99  ✅
子查询「B」 → 段落 B 得 0.98  ✅
   ↓ 合并
两段都拿到  ✅
```

**机制层面完全对上了。** 当时只知道「有效」，现在知道了**为什么**。

#### ⚠️ 那精确率 0.46 呢？—— 一个还没验完的新假设

既然精排不是「无脑放行邻居」，那「ReAct 架构的优缺点」返回 `[0, 1]` 就不该简单叫「噪音」：

```
chunk[0] 0.9995   ReAct 本体        → 能回答 ✅
chunk[1] 0.9990   Plan-and-Execute  → 但也提到了 ReAct，提供了对比视角
```

**⇒ 精确率 0.46 可能不是「系统的问题」，而是「`gold` 标得太窄」** —— 我们把 `gold` 定义成「唯一能完整回答的段落」，但 chunk[1] 对回答**确实有贡献**。

**这是个假设，还没有验证。** 但它指向一个很实在的问题：**`gold` 到底该不该只标一段？** 这是**标注标准**的问题，不是代码的问题 —— 而且它可能会让之前「精确率低」的结论**改判**。

#### 顺带：段落内部的格式也会影响分数（但别过度解读）

只改**段落**、查询固定：

```
原样（标题+正文）        0.0073
去掉标题行              0.0748    ← 高 10 倍
只留标题               0.0306
把标题重复两遍           0.0034    ← 更低
```

**「RAG 检索增强生成」这行标题反而把分数压低了。**

但要注意：**这些值全在 0.003~0.075 之间，全部远低于阈值 0.3** —— **它们都不改变最终结果**。

> **纪律：别在一个「不改变任何结果」的差异上做文章。**

### 第 13 课：复查 gold 的定义 —— 顺手修正了「阈值救不了」

#### 起点：第 12 课留下的一个假设

> 既然精排判「能不能回答」判得很准，那它返回的、我们标成「多余」的段落，
> 会不会其实**有贡献**？如果是，`precision 0.46` 就不是系统的问题，而是 `gold` 标得太窄。

#### 复查方法：两个**可计算**的线索

判「有没有贡献」最终要靠人读全文，但先算两个数能把范围缩小：

| 线索 | 说明 |
|---|---|
| **分差** | `gold 段最高分 − 多出段的分数`。差得越小 → 越可能是「gold 标窄了」 |
| **实词命中** | 查询里去掉停用词后的实词，多出的那一段命中了几个 |

`gold_review.py` 对每条「多给了」的查询打印：精排分、分差、实词命中、**多出那段的全文**。

#### 结果：假设只对了一小部分

```
有标准答案的查询里，5 条【多给了】段落，共多给 6 段
```

| 案例 | 多给的段落 | 全文里有答案吗 | 分差 |
|---|---|---|---|
| ReAct 优缺点 | chunk[1] P&E | **✅ 有贡献** —— 它说「相比 ReAct 的『边想边做』，它更适合需要全局规划的任务」，**这就是 ReAct 的一个缺点** | **0.0005** |
| P&E 优缺点 | chunk[2] 多 Agent | ❌ 噪音 —— 全段讲多 Agent，**没提 P&E** | 0.4136 |
| P&E 优缺点 | chunk[0] ReAct | ❌ 噪音 —— 讲 ReAct 自己的优缺点 | 0.4544 |
| 多 Agent 架构 | chunk[0] ReAct | ❌ 噪音 | 0.2465 |
| Agent 评测 | chunk[5] 可观测性 | ❌ 噪音 | 0.1473 |
| 一边思考一边调用工具 | chunk[1] P&E | ⚠️ 边界 —— 提到「边想边做」但只一句 | **−0.0142**（比 gold 还高！） |

**6 段里：1 段有贡献、1 段边界、4 段是真噪音。**

> **所以 `precision 0.46` 里只有约 1/6 能归到「`gold` 标窄了」。大部分是真问题。**

#### 真噪音的机制：**通用词的假重合**

| 案例 | 「命中查询实词」 | 真相 |
|---|---|---|
| P&E 优缺点 → chunk[2] | `优, 构, 架, 架构, 点, 缺, 缺点` **7/9** | **7 段里每段都有「架构」和「优缺点」！** |
| 多 Agent 架构 → chunk[0] | `agent, 构, 架, 架构` **4/5** | 「架构」是通用词 |
| **Agent 评测 → chunk[5]** | `agent, 测` **2/4** | ⚠️ **「观**测**性」vs「评**测**」—— 字面撞了，意思不同** |

⭐ **最后一条特别典型**：`测` 这个字在「可观测性」和「评测」里都有，但一个指追踪执行、一个指打分。精排看到这个字面重合，给了 **0.8525**。

**所以「同域邻居」的机制清楚了**：不是「主题相关」，而是**通用词的假重合**（架构 / 优缺点 / 测 / 点）。

#### ⭐⭐ 但真正挖出来的东西在「分差」那一栏

```
差 < 0.01（几乎并列）    2 段     ← 阈值救不了（区间只有 0.0005 宽）
差 0.01~0.1            0 段
差 > 0.1（明显更低）     4 段     ← 阈值【能】救
```

把所有需求列成一张表：

| 查询 | 想要的段落 | 它的分 | 要砍的段落 | 它的分 | 阈值要满足 |
|---|---|---|---|---|---|
| P&E 优缺点 | chunk[1] | 0.9998 | chunk[2] / [0] | 0.5861 / 0.5453 | **> 0.5861** |
| Agent 评测 | chunk[6] | 0.9998 | chunk[5] | 0.8525 | **> 0.8525** |
| 一边思考一边调用工具 | chunk[0] | **0.9310** | — | — | **< 0.9310** |

**三个约束有交集：`0.8525 < 阈值 < 0.9310`** —— 取 **0.9** 就能同时满足。

#### ⚠️ 而这意味着：第 4 课的「阈值救不了」**范围夸大了**

当时的论证是：

> 要「保留 0.9995、砍掉 0.9990」，阈值必须卡在 0.0005 宽的区间里；而另一条查询的 chunk[3] 被砍是因为它低于 0.3 —— 一个旋钮不可能同时做到这两件事。

**问题在于：把不同查询的需求混在一起论证了。** 展开看：

| 分差 | 段数 | 阈值能救吗 |
|---|---|---|
| **< 0.01**（几乎并列） | 2 | ❌ 救不了 —— 这里「饱和导致无分辨率」是真的 |
| **> 0.1** | 4 | ✅ **能救** |

而「多概念漏 chunk[3]（0.0073）」是**另一回事** —— 那个任何阈值都救不了（要靠查询分解）。**两件事被混成了一件。**

#### 实测：阈值 0.9

```
策略                  召回    精确    MRR    拒答
改前：阈值 0.3         0.91   0.76   0.95   7/8
改后：阈值 0.9         0.91   0.91   0.95   8/8
生产默认（不传参）       0.91   0.91   0.95   8/8   ← 回归检查：和改后一致 ✅

4 条改善，0 条变坏
```

**而且两个预测同时兑现**：

| 分段 | 预测 | 结果 |
|---|---|---|
| 分差 **> 0.1** 的 4 段 | 阈值能救 | ✅ 全部救回（P&E / 多 Agent / Agent 评测 / Langfuse 拒答） |
| 分差 **< 0.01** 的 1 段 | 阈值救不了 | ✅ 「ReAct 架构的优缺点」果然还是 `[0,1]`，精确 0.50 没动 |
| 多概念漏 chunk[3] | 与阈值无关 | ✅ 召回 0.67 → 0.67 没变 |

#### ⚠️ 但 0.9 不能直接搬走

```
那些 gold 段落的精排分：0.9995 / 0.9998 / 0.9997 / 0.9998 / 0.9310
```

**全都 ≥ 0.93** —— 这是 **7 段同域小语料**的特性：相关段落和查询「几乎完美匹配」。

**换成真实语料（跨领域、上千段），一个「确实相关但不够完美」的段落可能只有 0.6~0.8** —— **0.9 会把它砍掉，从「精确率低」变成「漏召回」。**

按我们自己写进专题 2 的原则：

> **阈值必须用真实数据量出来。样本小时它只是「当前数据下的最优」。**

**所以 0.9 是「这份 7 段语料下的最优」，不是通用值。**

#### 落地方式：改，但把标定条件写进代码

```python
# 精排分数的门槛：低于它就当作「不相关」，直接丢弃。
#
# ⚠️⚠️ 这是一个【在本语料上标定出来的值】，不是通用常数 —— 换语料必须重新标定。
#
# 标定过程（训练集 19 条，同一把尺子只动这一个变量）：
#     阈值 0.3 → 召回 0.91  精确 0.76  MRR 0.95  拒答 7/8
#     阈值 0.9 → 召回 0.91  精确 0.91  MRR 0.95  拒答 8/8
#   4 条改善、0 条变坏。为什么是 0.9：把 6 段「多返回」的段落按分差分成两档 ——
#     分差 > 0.1 的 4 段（0.5453~0.8525）：0.9 能干净砍掉，gold 段都在 0.93 以上
#     分差 < 0.01 的 1 段（0.9990 vs 0.9995）：任何合理阈值都砍不掉，只能靠查询分解
#
# ⚠️ 为什么不能直接搬到别的语料：
#   本语料只有 7 段、高度同域，所以「相关段落」的分数都挤在 0.93~0.9998。
#   真实语料里，一个「确实相关但不够完美」的段落可能只有 0.6~0.8，
#   0.9 会把它砍掉 —— 从「精确率低」变成「漏召回」。
#
# 重新标定的方法：改这个值 → 跑 `python -m retrieval.evaluate`，
#   看四个指标（召回 / 精确 / MRR / 拒答）有没有同时变好，别只看一个。
RERANK_THRESHOLD = 0.9
```

⭐ **为什么把这么多字写在代码里**：这个数字**看起来像个通用常数**（`0.9` 多自然啊），下一个人（包括三个月后的你）会直接复制走。**把「它是在哪标定的、什么时候会失效」写在它旁边，是唯一能挡住这件事的办法。**

（同一条原则见专题 9「把依据写进代码」。）

#### 这一课的两个收获

| 表面结果 | 真正的收获 |
|---|---|
| 精确 0.76 → 0.91 | ⭐ **第 4 课那条「阈值救不了」的结论，范围被我夸大了** —— 它只对「几乎并列」的段落成立 |
| `gold` 复查只找到 1/6 的问题 | ✅ **`gold` 的定义本身基本没问题** —— 「精确率低」是真问题，不是标注问题 |

## 四、关键问题专题

### 专题 1：四个指标各管一只眼睛

| 指标 | 一句话 | 坏了会怎样 | 完全看不见 |
|---|---|---|---|
| **召回** | 该找到的，找到了几成 | 回答不出来（资料明明有） | **多给的** |
| **精确** | 返回的，几成是需要的 | 回答里混进噪音 | **漏了的** |
| **MRR** | 对的排第几 | 排太靠后，被 `max_k` 截掉 | 前后的噪音 |
| **拒答** | 该说「不知道」时说了没有 | **硬答 → 幻觉** | 答得对不对 |

**实测证据**：「直接」类召回 1.00、MRR 1.00 —— **在加精确率之前，那个 0.46 是个黑洞。**

> **指标少一个，就少一只眼睛。坏掉的地方你看不见，还以为一切都好。**

### 专题 2：分数饱和之后，阈值失去分辨能力

精排分挤在 0.999 和 0.000 两极。后果：

| 后果 | 说明 |
|---|---|
| 阈值「怎么定都一样」 | 0.1 到 0.9 之间任何值结果相同 → **它从没被考验过** |
| 「分差」失真 | chunk[0] vs chunk[1] 在 logit 空间差 0.7，概率空间只差 0.0005 |

**这不是「调得不够好」，是判定层的问题得在别的零件上解。**

### 专题 3：同一旋钮，两个方向

| 问题 | 想要 | 
|---|---|
| 精确低（多返回了不该返回的） | 阈值**调高** |
| 召回漏（该有的被砍） | 阈值**调低** |

**而更深一层：要「保留 0.9995、砍掉 0.9990」，阈值得卡在 0.0005 宽的区间里 —— 这个旋钮根本没有这个精度。**

### 专题 4：我的判断被数据推翻了四次

| # | 我的判断 | 实际 | 为什么错 |
|---|---|---|---|
| 1 | 精排分是 logits，会有负数 | 是 Sigmoid 后的**概率** | 版本默认值变过（`model.py:425`） |
| 2 | 「近似无答案」会被高高兴兴返回 | **5/6 正确拒答** | cross-encoder 对「明显缺细节」的问题是**准确**的 |
| 3 | 返回的一半是「垃圾」 | 是**有对比价值的资料** | 过度解读了精确率 |
| 4 | **「它判相关，不判能作答」** | **正好相反：它判的就是「能不能回答」，而且判得很准**（第 12 课） | **做了一个看起来合理、但没做能证伪实验的机制解释** |

⭐ **第 4 条最值得注意，因为它和前三条的性质不同**：

| | 前三条 | 第 4 条 |
|---|---|---|
| 错在哪 | **读数**（指标没看全、过度解读） | **机制解释** |
| 怎么发现 | 补一个指标就露出来了 | **需要专门设计一个能证伪的实验**（扰动） |
| 危险程度 | 低（一眼能改） | **高 —— 它会被写进文档、当成前提，后面所有推理都建在它上面** |

**第 2、3 条的共同原因：我当时看的指标里没有精确率。**

> **凭直觉猜「哪里会坏」，猜错是常态 —— 这就是必须先建评测的理由。**

### 专题 5：尺子本身也要被检查 —— 三个层次

| 层次 | 坏法 | 本项目的实例 | 怎么发现 |
|---|---|---|---|
| **刻度值** | `gold` 标错 | 8 条全填 `[0]`，5 段从没被考过 | 统计 **gold 分布** |
| **刻度选择** | 指标漏了 / 指标饱和 | 漏了精确率；`Recall@5` 在 7 段上结构性饱和 | 摊开逐条结果看；想「这个指标在什么情况下会变」 |
| **量的对象** | 测的不是真正在用的那条路 | 评测调 `_retrieve`，而 MCP 服务调 `search`（虽然 `smart_query=False` 时等价） | **去读真正在用的调用点** |

**三个层次都坏过一次，而且都不报错。**

### 专题 6：留出集 —— 自己出题自己考

| | 训练集 | 留出集 |
|---|---|---|
| 用途 | 设计和调优，看多少遍都行 | **只看一次，看完定论** |
| 纪律 | — | 不参考结果设计、跑完不改规则、结果不好就认 |

**本项目最有说服力的证据**：

| 数据集 | 全开召回 | 智能召回 |
|---|---|---|
| 训练集 | 1.00 | **1.00**（看不出差别） |
| 留出集 | 1.00 | **0.93**（差 0.07） |

**没有留出集，会带着错结论上生产。**

### 专题 7：评测本身有噪声

`search(use_decompose=True)` 内部用 LLM 拆分，**同一策略、同一评测集，两次跑出不同的数字**：

| | 第一次 | 第二次 |
|---|---|---|
| 总体精确 | 0.71 | 0.76 |
| 换词精确 | 0.75 | 0.88 |

**差异 0.05，来自一条查询** —— 而我们在比较的差异**也是 0.05 量级**。

> **噪声的量级和你关心的差异量级一样大时，单次运行的数字不能当结论。**

由此：

| 说法 | 站得住吗 |
|---|---|
| 「智能 MRR 0.95 vs 全开 1.00，所以全开排序更好」 | ❌ 差的 0.05 来自一条查询，噪声也是 0.05 |
| 「智能召回 0.91 → 1.00」 | ✅ 差 0.09，来源清楚（那两条多概念） |
| 「LLM 调用从 19 次降到 4 次」 | ✅ 确定数，不含噪声 |

### 专题 8：用 LLM 做「理解」，用规则做「执行」

这条在 MCP 那一课已经出现过一次。这里再次验证：

| 做法 | 结论 |
|---|---|
| 用 LLM 判断「要不要拆」+ 拆 | ✅ 准，但每次 0.7 秒 |
| 用关键词规则判断「要不要拆」 | ❌ 留出集上失败 —— 因为真正的工作是**理解**（词内含义、改写），不是**匹配** |

**「智能分解」的失败不是「关键词不够全」，是**把「理解」的任务交给了「匹配」**。**

（但也别反向过头：0.7 秒的 LLM 调用在质量收益面前**不值得优化** —— 这是过早优化。）

### 专题 9：把依据写进代码

`smart_query` 的默认值从 `False` 改成 `True` 时，**把实测数字和「为什么规则替代不了」一起写进了注释**。

因为：

- 三个月后看到 `smart_query: bool = True` 的人（包括你自己）只会想「为什么默认开？是不是随便定的？」
- **默认值的依据不写在它旁边，就等于没有依据** —— 下一个人可能随手改回去

> **和「错误信息是操作说明」是同一个道理：代码里每个「反直觉的默认值」都应该自带解释。**

### 专题 10：⭐「有原理的修」和「凭观察的修」

这一路做了两次「改进」，结果截然相反。放在一起看非常刺眼：

| | 智能分解**规则** | **停用词表** |
|---|---|---|
| 怎么来的 | 从训练集 19 条里**看**出「含『和』字大概要拆」 | 从**分数拆解**推出「疑问句功能词被当实词了」 |
| 有没有因果 | ❌ 只是相关 | ✅ **有机制**（chunk[0] 的 91.5% 来自「什么」） |
| 训练集表现 | 召回 1.00（和全开一样） | 92.86% → **100%** |
| 留出集表现 | **0.93**（差 0.07，过拟合暴露） | 未测（但内容通用） |
| 本质 | **观察到的模式** | **通用先验**（任何中文 IR 都要停用词） |

> **凭观察看到的模式，换个数据集就失效。从机制推出来的修复，直接生效。**

**推论：判断一个「发现」靠不靠得住，先问它有没有机制解释。**

| 有没有机制 | 怎么办 |
|---|---|
| **有** | 机制本身就是泛化性的一部分，可以直接用 |
| **没有** | 只能靠**留出集**挡 —— 而且留出集只能用一次 |

### 专题 11：稠密 vs 稀疏，什么时候谁强

实测（k=1，按查询类型拆开）：

| 查询类型 | 向量 | BM25 | 为什么 |
|---|---|---|---|
| **直接**（用原文词） | **100%** | 75% | BM25 的词面匹配会被「优缺点在别处也出现」带偏 |
| **换词**（改写了说法） | 75% | **100%** | 向量把语义模糊化了；BM25 抓不住同义，**但至少不误导** |

**整体上 BM25 还打赢了向量**（92.86% vs 85.71%），原因和「向量分数地板」是同一个现象：

| | 向量 | BM25 |
|---|---|---|
| 语料**同域**（7 段都讲 Agent） | 语义空间里互相很近，分数全挤在 0.42~0.46，**分不开** | 不受影响 |
| 查询含**精确词**（RAG / Langfuse） | 被语义平均掉了 | **只在某几段出现 → 区分度极高** |

> **语料越同域、查询越依赖精确词，向量的优势越小、BM25 的优势越大。**

（反过来说：如果语料跨很多领域、查询是口语化改写，向量会明显更强。**这不是「谁更好」，是「谁的假设更符合你的场景」。**）

### 专题 12：候选预算是个隐藏的旋钮

这次的实验全部建立在「把预算压到 1~3」上。而系统现在的预算是 **`coarse_k = 20`**，语料只有 7 段。

**预算决定了「候选池」有多大，也就决定了召回层有没有在干活：**

| 预算 | 候选池 | 召回层的作用 | 混合检索的价值 |
|---|---|---|---|
| 20（>语料段数） | = 全集 | **没有作用** | **白加** |
| 3 | 收紧 | 真的在筛 | 看情况 |
| 1 | 最紧 | 筛得最狠 | **明显有用**（+7.14%） |

**而且预算还改变「什么方法更好」的结论**：

```
k=1 → 融合最好（78.57%）
k=2 → 融合反而最差（85.71% vs 92.86%）
k=3 → 全到天花板，什么都测不出
```

> **「哪个方法更好」这个问题，离开「预算多少」是没有答案的。**

这跟「阈值不能跨语料搬」是同一类陷阱：**参数之间是有耦合的，别指望一个全局最优。**

### 专题 13：串联系统里，优化上游可能是白干

链路是**串联**的：

```
召回层 → 精排层 → 阈值 → 结果
```

**每一层都是一道门。上游改得再好，只要下游一道门关着，结果就不会动。**

实测：候选池的召回从 **85.71% → 100%**（真实提升），**最终结果 0/19 条变化** —— 因为精排给那些段落的分数是 `0.0073`，阈值照样砍。

| 症状 | 你以为的瓶颈 | 真正的瓶颈 |
|---|---|---|
| 该找到的没找到 | 召回层 | **可能是精排**（进池了但被判无关） |
| 返回一堆不相关的 | 阈值 | 可能是精排（分数都偏高） |

**怎么定位？逐层测量：**

| 层 | 用什么工具量 |
|---|---|
| 召回层 | `recall_lab.py`（把下游拿掉，只看候选池） |
| 整条链路 | `evaluate.py`（看最终四个指标） |

⭐ **如果「召回层提升」和「整条链路不变」同时出现 —— 瓶颈就在召回层下游。**

> **推论：任何一层指标的改善，都不等于系统变好。要拿最终结果的那把尺子复核。**

这也是「量的对象」那个陷阱在**纵向**上的版本：之前是「测错了函数」（横向），现在是「测错了层」（纵向）。

### 专题 14：⭐「机制解释」错了最难发现

第 12 课推翻了一条**已经写进文档的结论**。它和前三次判断失误性质不同：

| | 读数错 | **机制解释错** |
|---|---|---|
| 例子 | 「指标没看全」「过度解读精确率」 | 「它判相关不判能作答」 |
| 怎么发现 | 补一个指标就露出来了 | **需要专门设计一个能证伪的实验** |
| 危险程度 | 低 —— 一眼能改 | **高 —— 它会被当成前提，后面所有推理都建在它上面** |

**为什么它最难发现**：因为**它不产生矛盾的数字，只产生「解释得通的说法」**。

「它判相关不判能作答」这个说法，当时能解释我们看到的两条数据 —— 而且听起来很专业（cross-encoder 本来就是做相关性排序的）。**它不缺合理性，缺的是「有没有被验证过」。**

#### 怎么防

| 做法 | 说明 |
|---|---|
| **问一句「这个解释，能做个实验证伪吗？」** | 不能证伪的解释，就只是个说法，别写进文档当结论 |
| **做【扰动实验】** | 固定一个变量、只动另一个，看输出怎么变 —— 这是打开黑盒唯一的办法 |
| **把「解释」和「观测」分开写** | 观测是数据（`chunk[3] = 0.0073`），解释是推断（可能错）。**写文档时标清楚哪个是哪个。** |

**这次就是靠扰动实验（调换主体顺序 / 只留一个主体）一击命中的。**

### 专题 15：精排判的是「能不能回答」，判得很准

第 12 课的结论，值得单独记：

| 查询 | 段落 | 分数 | 精排的「判断」 |
|---|---|---|---|
| 「RAG」 | chunk[3] | **0.9784** | 这一段就是答案 ✅ |
| 「多 Agent 协作和 RAG 有什么不同」 | chunk[3] | **0.0073** | **单段答不了「两者的不同」** ✅ 这个判断是对的 |
| 「ReAct 架构的优缺点」 | chunk[1] | 0.9990 | chunk[1] 提到了 ReAct 并做了对比 → **确有贡献** ✅ |

**它不是「无脑给同域邻居高分」，而是一个相当准的「能否作答」判别器。**

⇒ **精排不是瓶颈，架构才是**：**问一个复合问题，却期望单段来回答。**

**推论**：遇到「该找到的没找到」，先别怀疑精排 —— **先问「这个查询是不是需要多段」**。需要的话，解法是**查询分解**，不是换模型、不是调阈值。

### 专题 16：⭐ 机制解释错的第二种形式 ——「范围推广」

专题 14 记了「机制解释错」的第一种形式：**解释本身错了**（「判相关不判能作答」）。

第 13 课又撞上第二种形式：**解释是对的，但适用范围被我放大了**。

| | 第 12 课（专题 14） | 第 13 课（本专题） |
|---|---|---|
| 结论 | 「判相关不判能作答」 | 「阈值救不了」 |
| 错在哪 | **解释本身错** | **解释对，但只对一部分情况成立** |
| 真相 | 它判的就是「能不能回答」 | 只对**分差 < 0.01** 的段落成立；分差 > 0.1 的 4 段阈值都能救 |

**它是怎么被放大的**：

```
观测 1：某条查询里，正确答案 0.9995、邻居 0.9990 → 区间只有 0.0005 宽
观测 2：另一条查询里，正确答案 0.0073 被阈值砍了 → 需要阈值 < 0.3
结论  ：一个旋钮不可能同时做到 → 阈值这个零件不行
```

**错误出在第 3 步**：把**不同查询的需求**混在一起论证，得出「不可能」。而实际上**它们的分差区间并不重叠**，存在可行解。

#### 怎么防「范围推广」

| 做法 | 说明 |
|---|---|
| **写结论时，把「成立条件」一起写** | 不是「阈值救不了」，而是「**对分差 < 0.01 的段落**，阈值救不了」 |
| **给结论配一个「反例搜索」** | 主动去找**不满足**这个结论的样本 —— 第 13 课就是靠「按分差分档」找到那 4 段的 |
| **把观测数据分档，而不是整体下一个判断** | 「6 段多返回」整体看是「阈值松」，**分档后才是「2 段救不了 / 4 段救得了」** |

> **一句「XX 不行」听起来很有洞察力，但它通常只是「XX 在某个条件下不行」。**
> **把条件写出来，比结论本身重要。**

## 六、经验教训

### 1. 先建尺子，再动手

没有评测，一切优化都是猜。而且**猜错是常态** —— 本次我的判断被推翻了**四次**，其中一次还是**已经写进文档的机制解释**（见专题 14）。

### 2. 「结果正确」和「你的机制在起作用」是两件事

第 4 课的 `id=3 = False`（写操作项目）和第 6 课的对比实验是同一个道理：**只有把机制拆掉看到结果变坏，才能说这两者有因果。**

### 3. 尺子本身要检查 —— 三个层次

**刻度值**（gold 分布）、**刻度选择**（指标够不够、饱不饱和）、**量的对象**（是不是真正在用的那条路）。

三个都坏过一次，而且都不报错。

### 4. 指标少一个，就少一只眼睛

召回 1.00 把精确 0.46 完全盖住了。**坏掉的地方你看不见，还以为一切都好。**

### 5. 数字要能精确归因

「精确率掉 0.05」→ 追到**一条查询**上，`0.50 ÷ 11 = 0.045`。**不是「感觉变了」，是「这一条变了，别的都没动」。**

### 6. 留出集是唯一能挡住过拟合的东西

**自己出题、自己考、自己打分** —— 分数当然好看。而留出集抓到了训练集看不见的 0.07。

**而且纪律②（跑完不改规则）比纪律①更重要**：允许反复调整的留出集，等于没有留出集。

### 7. 噪声和差异同量级时，单次结果不能当结论

LLM 驱动的环节会给评测带来 0.05 量级的抖动。**先把「确定性数字」（LLM 调用次数）和「有噪声的数字」（指标）分开看。**

### 8. 「看起来像」和「实际是」是两件事

- 「文字上像复合问题」≠「需要拆开检索」（对抗-假漏判）
- 「返回了多一段」≠「那一段没用」（可能是**有对比价值的资料**，而不是噪音）
- 「分数很低」≠「不相关」，也可能是「饱和到 0」
- ⚠️ ~~「相关」≠「能作答」~~ —— **这条推翻了**：精排判的**就是**「能不能回答」，而且判得很准（第 12 课）

### 9. 用 LLM 做理解，用规则做执行

关键词规则替代不了 `decompose` —— 因为真正的工作是**理解**（词内含义、查询改写），不是**匹配**。

**但也别反向过头**：0.7 秒的 LLM 调用在质量收益面前不值得优化 —— **那是过早优化**。

### 10. 把依据写进代码

`smart_query: bool = True` 旁边必须有实测数字和「为什么不能用规则替代」。**默认值的依据不写在它旁边，就等于没有依据。**

### 11. 失败要留档

这次的 commit message 里**特意记下了失败的那条**：

> 「文字规则版智能分解在留出集上失败，因为 decompose 还会改写查询、拆开词内含义，规则原理上做不到」

**这条比成功的那条更值钱** —— 它挡住了一条以后很可能再走一遍的弯路。

### 12. 过早优化

**先量，再决定要不要优化。** `decompose` 平均 0.7 秒 —— 讨论了三课的「怎么让它变便宜」，答案在量完之后变成了「不需要」。

### 13. ⭐ 优先做「有原理的修」

这一路做了两次改进，结果相反：

| | 凭观察的修 | 有原理的修 |
|---|---|---|
| 例子 | 智能分解规则（从训练集里看出「含『和』字要拆」） | 停用词表（从分数拆解推出「疑问句功能词被当实词」） |
| 结果 | 留出集上**失败** | 一招生效 |

**判据：这个改动，我能说清它为什么会有用吗？**

- **能** → 机制本身就是泛化性，可以直接用
- **不能** → 只能靠留出集挡，**而留出集只能用一次**

### 14. 参数之间是有耦合的

「哪个方法更好」这个问题，**离开「候选预算多少」是没有答案的**：

```
k=1 → 融合最好（78.57%）
k=2 → 融合反而最差（85.71% vs 92.86%）
k=3 → 全到天花板，什么都测不出
```

同理，阈值也不能跨语料搬（记忆库用 0.40，这里无关段落就有 0.42~0.46）。

**别指望一个全局最优的参数。**

### 15. 分数「可加」就等于「可解释」

BM25 的总分是**每个 token 贡献之和**，所以能逐项拆开：

```
chunk[0] 的 5.338 分里，4.884 分（91.5%）来自「什」「什么」「么」
```

**向量的相似度做不到这一点** —— 它是一个整体值，你没法说「这个 0.42 里，'RAG' 贡献了多少」。

> **当你要「找根因」而不只是「比好坏」时，可解释的模型有独立的、不可替代的价值。**

这也是这次能一击命中的原因：如果只有向量，我最多知道「chunk[3] 排第 4」，**永远不知道差在哪。**

### 16. ⭐ 串联系统里，先找瓶颈再优化

链路是 `召回 → 精排 → 阈值` **串**起来的。**上游改得再好，下游一道门关着，结果就是不动。**

实测：候选池召回 **85.71% → 100%**，最终结果 **0/19 条变化**。

**定位方法：逐层量。**

```
recall_lab.py   → 只看召回层
evaluate.py     → 看整条链路
两者不一致     → 瓶颈在召回层下游
```

> **任何一层指标的改善，都不等于系统变好。要拿最终结果的那把尺子复核。**

**这次的「白干」比「看起来成功」值钱得多** —— 如果没做整链路复核，会带着「召回 100% = 系统变好了」的错结论去交付。

### 17. 工具要「够到决策」，不能只够到中间指标

`hybrid_lab` 测得没错（召回确实涨了），但它**停在半路上** —— 它看不到精排和阈值。

**判断一个测量工具好不好，问一句：它的输出能直接支撑决策吗？**

- 不能 → 它只是**诊断工具**（`recall_lab` / `bm25_dig`），不是**验收工具**
- 能 → 它才是 `evaluate.py`

**两个都要有，但别把诊断工具的结论当验收结论。**

### 18. 落地前先想清「用哪种接法」

同样的目的（把 BM25 接进链路），有两种接法，结论完全不同：

| 接法 | 适用 |
|---|---|
| **并集**（向量 top-k ∪ BM25 top-k → 精排） | **下游有精排**时 —— 召回层只要「不丢」，排序交给精排 |
| RRF 融合后取 top-k | **下游没有精排**时 —— 融合要同时承担排序 |

**选错的代价**：用 RRF 会**丢东西**（实测 k=2 时丢过一个），而并集只是多几个候选。

> **一个算法「有没有用」，取决于它放在链路的哪一段。**

### 19. ⭐ 机制解释需要「能证伪的实验」才算结论

第 12 课推翻了一条已经写进本文档的结论：

> ~~「cross-encoder 判相关不判能作答」~~

**它错在哪**：不是错在「不合理」—— 它听起来很专业（cross-encoder 本来就是做相关性排序的），而且当时能解释我们看到的数据。**它错在从来没被验证过。**

**这类错最难发现**：

| | 读数错 | 机制解释错 |
|---|---|---|
| 怎么暴露 | 补一个指标就露出来了 | **需要专门设计一个能证伪的实验** |
| 危险 | 一眼能改 | **被当成前提，后面所有推理都建在它上面** |

**做法**：

1. **写完一个解释，问一句「这个能做个实验证伪吗？」** 不能证伪的，标成「推测」，别写成「结论」
2. **用扰动实验**：固定一个变量、只动另一个，看输出怎么变 —— 这是打开黑盒唯一的办法
3. **写文档时把「观测」和「解释」分开**：`chunk[3] = 0.0073` 是**数据**；「因为查询是复合的」是**推断**。两者都写，但要标清楚

**这次能一击命中，靠的就是「只调换两个主体的顺序」这一个设计。** 它足够简单，也足够致命：**如果模型在看位置，调换后分数必须互换。它没换 —— 假设就死了。**

### 20. 遇到「该找到的没找到」，先问「这个查询需要几段」

第 12 课之后，排查顺序应该改：

| 旧顺序 | 新顺序 |
|---|---|
| 1. 怀疑精排不准 | 1. **这个查询是不是需要多段？**（复合 / 关系型问题） |
| 2. 调阈值 | 2. 需要 → **查询分解**（已验证有效） |
| 3. 换模型 | 3. 不需要 → 再去看召回层、精排层 |

**因为精排判「能不能回答」判得很准** —— 它给低分，通常是因为**真的没有单段能回答**。

### 21. ⭐ 结论要连「成立条件」一起写

第 13 课推翻了「阈值救不了」这个结论 —— 但**不是推翻全部**：

| 说法 | 对不对 |
|---|---|
| 「阈值救不了」 | ❌ **太宽** |
| 「对分差 < 0.01（几乎并列）的段落，阈值救不了」 | ✅ **准确** |
| 「对分差 > 0.1 的段落，阈值能救」 | ✅ **实测 4 段全救回来了** |

**一句「XX 不行」听起来很有洞察力，但它通常只是「XX 在某个条件下不行」。**

**写结论时把条件写出来，比结论本身重要** —— 因为别人（和你自己）会把这个结论往别的场景上套。

### 22. 参数的「值」和「标定条件」必须写在一起

把 `RERANK_THRESHOLD` 从 `0.3` 改成 `0.9` 时，在代码里写了 15 行注释，说明：

- 标定过程（四个指标各自怎么变的）
- 为什么是 0.9（分差分析）
- **什么时候会失效**（换语料、特别是跨领域大语料）
- **怎么重新标定**

**为什么值得写这么多**：`0.9` 看起来像个**通用常数**（多自然），下一个人会直接复制走。**把「它是在哪标定的」写在它旁边，是唯一能挡住这件事的办法。**

> **一个没有标定条件的参数值，等于一个谣言。**

### 23. 复查「评测标准」和复查「代码」一样重要

第 13 课的起因是「精确率低」，但复查后发现：

| 问题 | 复查结果 |
|---|---|
| `gold` 标得太窄了吗？ | **只 1/6 是** —— 定义基本没问题 |
| 那是谁的错？ | **阈值太松**（4/5 的多余段落分差 > 0.1） |

**如果不去复查「标准本身」，只会一直怀疑代码。**

**而复查标准的方法**：把「多出来的结果」一条条摊开、读全文、算分差 —— **不是看汇总数字**。

### 容易忘的细节

- **`-m` 和直接跑文件，`sys.path[0]` 不一样** —— `python file.py` 是**文件所在目录**，`python -m pkg.mod` 是**当前工作目录**。所以必须在项目根目录用 `-m`。
- **每次跑要先加载两个模型**（约 30 秒）。
- **`decompose` 用 LLM，结果有随机性** —— 同一个查询两次跑可能拆出不同的子查询，所以**评测数字本身有 0.05 量级的抖动**。
- **`search(use_decompose=True)` 比 `_retrieve` 慢约 0.7 秒**。
- **改了 `mcp/mcp_server.py` 后，Cursor 里的 MCP Server 不会热重载** —— 要重启（第一次调用前等约 30 秒模型加载），日志里应出现 `优化=True`。
