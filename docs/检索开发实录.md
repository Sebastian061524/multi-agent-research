## 一、项目概览

### 目标

调研项目里有三段代码**共用同一个检索层**：

```
调研 Agent 查资料   ─┐
记忆库查历史会话     ─┼─→  BGE 向量检索 + cross-encoder 精排  →  research_docs
MCP 知识库服务       ─┘
```

**它好一分，三个项目一起好一分。** 但它一直是个黑盒：出了问题只知道「查不到」，不知道该改哪里。

### 起点：两个说不清的问题

| 问题 | 症状 |
|---|---|
| 分不清「真没有」还是「措辞没对上」 | 同样的阈值下，有的查询返回空、有的返回一堆不相关的，看不出规律 |
| 调参没有方向感 | 阈值、模型、prompt 都试过，改完只能凭感觉判断好坏 |

第二个的原因是：**一直没造出一把尺子。**

### 最终交付

| 类别 | 内容 |
|---|---|
| **尺子** | 训练集 19 条 + 留出集 14 条，人工标注标准答案 |
| **工具** | 逐级拆解 / 评测 / 失败诊断 / 评测集体检 / 成本测量 |
| **基线数字** | 召回 0.91 · 精确 0.76 · MRR 0.95 · 拒答 7/8 |
| **一次落地** | MCP 服务的 `smart_query` 默认值 `False` → `True`（附实测依据） |

### 技术栈

| 组件 | 用什么 |
|---|---|
| 嵌入（粗筛） | `BAAI/bge-small-zh-v1.5`，512 维，`normalize_embeddings=True` |
| 精排 | `BAAI/bge-reranker-base`（CrossEncoder） |
| 框架 | `sentence-transformers 6.1.0` |
| 语料 | `research_docs/sample_ai_agents.txt`，**7 段** |

## 二、背景知识：检索是怎么工作的

### 2.1 六个环节

```
research_docs/*.txt
   ↓ ① 切块：按 "\n\n" 切段落，丢掉 ≤20 字的
7 个 chunk
   ↓ ② 编码：bge-small-zh-v1.5
embeddings（7 × 512）

查询进来 →
   ↓ ③ 编码成向量
   ↓ ④ 相似度 = embeddings @ qv          ← 粗筛（bi-encoder）
top coarse_k = 20
   ↓ ⑤ 精排：bge-reranker-base           ← cross-encoder 逐条重打分
   ↓ ⑥ 过滤 rr_scores < 0.3，最多取 max_k = 5
结果
```

**六个环节，每一环都可能出问题 —— 而它们出的问题看起来一模一样，都叫「查不到」。**

> **这就是「调参没有方向感」的根源**：你只有一个观测点（最后的输出），中间有六级。

**顺带解释了为什么正好是 7 段**：文件第 1 行的标题「大语言模型 Agent 的主流架构」只有 16 个字，被 `len(para) > 20` 这个过滤条件挡掉了。

### 2.2 为什么必须分开量

「检索效果不好」其实是几种**完全不同的病**，药也完全不同：

| 症状 | 病因 | 该动哪个零件 |
|---|---|---|
| 该找到的没找到 | 表示 / 召回问题 | 查询改写、混合检索 |
| 找到的排太后面 | 排序问题 | 精排模型、融合策略 |
| 返回一堆不相关的 | 判定问题 | 阈值、判定逻辑 |

**混在一个数字里看，永远不知道该改哪。**

## 三、开发过程（7 课）

### 第 1 课：拆开检索机

**先做的事不是修，是看。** 写 `anatomy.py`，把一个查询在**每一级**的分数都打出来。

#### 发现 1：向量粗筛是**空转**的

```python
coarse_k = 20                                    # main.py:115 默认值
idx = scores.argsort()[::-1][:coarse_k]          # 7 条里取 top-20 = 全部
candidates = [chunks[i] for i in idx]
rr_scores = reranker.predict(pairs)              # 对全部 7 条打分
order = rr_scores.argsort()[::-1]                # ← 按精排分重新排
```

**库里只有 7 段，粗筛保留 20 个** → `[:20]` 等于全部。而后面 `order` 是按 `rr_scores` 重排的，**向量分的排序用都没用上**。

`anatomy.py` 里的验证：

```
_retrieve 取到：['ReAct 架构...', 'Plan-and-Execu...']
纯精排   取到：['ReAct 架构...', 'Plan-and-Execu...']
两者完全相同：True
```

> **结论：当前检索 100% 由 cross-encoder 决定。**
> 你以为在开一台两级检索机，实际上只有一个零件在干活。

（注意：向量层**不是不行** —— 它把正确段落排在了第一，向量分 `0.7490` vs 第二名 `0.6035`。它是**没接上**。）

#### 发现 2：精排分是**概率**，不是 logits

我原本预测 `CrossEncoder.predict()` 返回原始 logits（会看到负数）。**这个预测错了。**

查了源码（`sentence_transformers 6.1.0`，`cross_encoder/model.py:425`）：

```python
    def get_default_activation_fn(self):
        if self.num_labels == 1:
            return nn.Sigmoid()
```

reranker 就是 `num_labels = 1`，所以**默认已经套了 Sigmoid** —— 分值在 `[0, 1]`，是概率。

> **教训**：「CrossEncoder 返回 logits」这个说法流传很广，但**这个默认值在版本历史上变过**。
> 属于那类「会随版本变、又不会报错」的默认值。

#### 发现 3：精排分是**双峰饱和**的

```
chunk[0] +0.9995   ← 正确（ReAct）
chunk[1] +0.9990   ← Plan-and-Execute
chunk[2] +0.0689
chunk[6] +0.0000
chunk[4] +0.0001
chunk[3] +0.0000
chunk[5] +0.0000
```

分数**全挤在两头**，中间是空的。把概率反推回 logit 就清楚了：

| 概率 | 反推的 logit `ln(p/(1-p))` |
|---|---|
| 0.9995 | **+7.6** |
| 0.9990 | **+6.9** |
| 0.0689 | −2.6 |
| 0.0000 | < −9.9 |

**两个后果**：

1. **阈值 `0.3` 在这份数据上「怎么定都一样」** —— 从 0.1 到 0.9 之间任何值，结果完全相同。**它从来没被真正考验过。**
2. **在饱和区，概率空间几乎没有分辨率** —— chunk[0] 和 chunk[1] 在 logit 空间差 **0.7**，取完 Sigmoid 后只差 **0.0005**。所以「用 top1 和 top2 的分差判断这次检索可不可信」这条路，在饱和区会失真。

#### 发现 4：「相关」≠「能作答」

查询是 **「ReAct 架构的优缺点」**，而**讲 Plan-and-Execute 的段落拿到了 0.9990**，几乎和正确答案（0.9995）并列。

因为：

> **cross-encoder 判的是「这段文本和这个查询相关吗」，不是「这段文本能回答这个问题吗」。**

两个 chunk 都在讲「Agent 架构」这个主题，所以对 reranker 来说**都算相关**。它的训练目标是**排序**，不是**判定能否作答**。

**而 `RERANK_THRESHOLD = 0.3` 是一个「相关性」阈值，被当成了「能不能回答」的判据。**

（这个现象后来在**精确率**上现了原形 —— 见第 3 课。）

### 第 2 课：建尺子

#### 三条标注纪律

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **人工标注，不许让 LLM 判分** | 7 段语料成本极低；用 LLM 判分 = 用另一个不可靠的东西衡量不可靠的东西 |
| 2 | **`gold` 的语义是「能回答」，不是「相关」** | 现有的 `RERANK_THRESHOLD` 犯的正是「把相关当成能作答」的错，尺子不能也这么定义 |
| 3 | **不许先看检索结果再标注** | 否则标准答案会被**被测系统**带偏，你测的就成了「它和自己一致吗」 |

#### 五类查询

| 类型 | 条数 | 作用 |
|---|---|---|
| 直接 | 4 | 用文档里的原词 |
| 换词 | 4 | 意思一样，但不出现文档里的关键词 |
| 多概念 | 3 | 需要不止一段拼起来 |
| **近似无答案** | **6** | **主题相关，但问的细节库里没有** |
| 无关 | 2 | 完全不相干 |

#### ⭐ 为什么「近似无答案」必须是**最多**的一类

如果标注的查询全是「库里能回答的」，那测的只是：**找得到的时候能不能找到**。

而真正的痛点完全没被测到：**找不到的时候，系统会不会硬答。**

**这类查询的特征**：主题词一定命中（ReAct / Langfuse / 向量数据库……），所以向量分和精排分都会**很高**，但正确答案是**拒答**。

**七条现成的来源**（拿着每一段问「哪些细节没写」）：

| 库里提到的 | 库里**没**说的 | 可以出的查询 |
|---|---|---|
| [5] Langfuse、LangSmith | 哪个更好、多少钱 | 「Langfuse 和 LangSmith 哪个便宜」 |
| [4] 长期记忆用向量数据库 | 用哪个库、怎么选 | 「长期记忆该选 Milvus 还是 Chroma」 |
| [4] 短期记忆受上下文窗口限制 | 窗口到底多大 | 「上下文窗口最大是多少 token」 |
| [0] ReAct 的优缺点 | 提出年份、论文 | 「ReAct 是哪一年提出的」 |
| [2] 四种协作模式的名字 | 每种怎么实现 | 「Debate 模式具体怎么落地」 |
| [6] LLM 作为裁判 | 它自己准不准、有没有偏见 | 「LLM 当裁判会不会有偏见」 |

#### ⚠️ 然后我犯了一个典型错误

第一次提交的评测集里，**8 条 `gold` 全是 `[0]`** —— 从模板复制 `query` 时忘了改 `gold`。

写了个「评测集体检」工具（`check_eval_set.py`），用**分布**一眼抓出来：

```
chunk[0]   11 次  ███████████
chunk[1]    3 次  ███
chunk[2]    0 次
chunk[3]    0 次
chunk[4]    0 次
chunk[5]    0 次
chunk[6]    0 次
```

**7 段语料里有 5 段从来没被考过。**

**这个错误不报错。** 而且后果最恶劣：

| | |
|---|---|
| `gold` 里 `chunk[0]` 出现 11 次 | 系统也经常返回 `chunk[0]`（它是 ReAct 段，向量分最高） |
| → Recall 看起来很高 | → **评测显示「检索效果不错」** |

> **一把永远显示及格的尺子。**

改正之后：7 段全覆盖，分布均匀，「应该拒答」的占比从 31% 升到 **42%**。

### 第 3 课：量基线

#### 第一版指标漏了一样东西

第一版只量了**召回 / MRR / 拒答**。结果：

```
类型             条数   Recall@5     MRR       拒答正确
直接              4       1.00    1.00          —
换词              4       1.00    0.88          —
多概念             3       0.67    1.00          —
------------------------------------------------------------
```

**看起来很好** —— 直到把逐条结果摊开：

| 查询 | 取到 | gold | 返回段数 | 其中相关 | **精确率** |
|---|---|---|---|---|---|
| ReAct 架构的优缺点 | `[0, 1]` | `[0]` | 2 | 1 | **0.50** |
| Plan-and-Execute 架构的优缺点 | `[1, 2, 0]` | `[1]` | 3 | 1 | **0.33** |
| 多 Agent 架构 | `[2, 0]` | `[2]` | 2 | 1 | **0.50** |
| Agent 评测 | `[6, 5]` | `[6]` | 2 | 1 | **0.50** |

**`Recall@5 = 1.00` 让人以为「检索很好」，实际上返回的东西一半以上是多余的。**

补上精确率之后的完整基线：

```
类型             条数      召回      精确     MRR       拒答正确
直接              4    1.00    0.46    1.00          —
换词              4    1.00    0.88    0.88          —
多概念             3    0.67    1.00    1.00          —
近似无答案           6       —       —       —        5/6
无关              2       —       —       —        2/2
------------------------------------------------------------
总体             19    0.91    0.76    0.95        7/8
```

#### ⭐ 而 `Recall@5` 在这个语料上本来就是个**哑指标**

库只有 7 段，`coarse_k = 20` 取全部，**候选池就是全集**。唯一的门是阈值 —— 所以**只要过了 0.3 就一定被返回，召回几乎不可能低**。

`直接` / `换词` 两类 `Recall@5 = 1.00` 是**结构性饱和**，不是「检索效果好」。

> **选了一个测不出差别的指标。**

#### 以及「相关 ≠ 能作答」终于现形

它没有表现为「该拒答的却高高兴兴返回」（那个预测错了，见专题 4），而是**精确率**：

```
查询：ReAct 架构的优缺点
gold = [0]          ← 只有这一段【能回答】
返回 [0, 1]         ← chunk[1] 是「相关，但不是答案」
精确 = 0.50
```

#### 三个失败案例

| 查询 | gold | 取到 | 问题 |
|---|---|---|---|
| 多 Agent 协作和 RAG 有什么不同 | `[2, 3]` | `[2]` | **chunk[3] RAG 被阈值砍了** |
| Agent 的记忆机制和 RAG 有什么不同 | `[3, 4]` | `[4]` | **chunk[3] RAG 又被砍了** |
| Langfuse 和 LangSmith 哪个便宜 | `[]` | 1 段 | 唯一一个「该拒答却答了」 |

#### 一个矛盾

| 问题 | 说明什么 | 想怎么修 |
|---|---|---|
| 「直接」精确率只有 0.46 | 阈值**太松** | **调高**阈值 |
| 「多概念」漏了 2 条 | 阈值**太紧** | **调低**阈值 |

**同一个旋钮，两个方向的需求。**

### 第 4 课：逐级诊断

**不猜，把每条失败查询的每一级分数打出来。** `diagnose.py`：

```
查询：多 Agent 协作和 RAG 有什么不同     gold = [2, 3]

  [2] 多 Agent 协作      精排 +0.9881   ✅ 过  ★
  [3] RAG 检索增强生成    精排 +0.0073   ❌ 被砍 ★
  其余 5 段              精排 < 0.009

查询：Agent 的记忆机制和 RAG 有什么不同    gold = [3, 4]

  [4] 记忆机制           精排 +0.9908   ✅ 过  ★
  [3] RAG               精排 +0.0326   ❌ 被砍 ★
  其余 5 段              精排 < 0.013

查询：Langfuse 和 LangSmith 哪个便宜    gold = []
  [5] Agent 的可观测性    精排 +0.3093   ✅ 过  ← 刚超过 0.3
  其余 6 段              精排 +0.0000
```

#### 死因完全不同

| 案例 | gold 的精排分 | 真正死因 |
|---|---|---|
| 多 Agent 协作和 RAG | chunk[3] = **0.0073** | **查询需要拆开** |
| 记忆机制和 RAG | chunk[3] = **0.0326** | 同上 |
| Langfuse 哪个便宜 | chunk[5] = **0.3093**（刚过线） | 判定边界太紧 |

#### ⭐⭐ 前两条的真相：**查询形式**

**同一个模式，两次**：查询是「**A 和 B 有什么不同**」这种**比较型问题**，reranker 把 **A 段给到 0.99**，把 **B 段给到 0.00~0.03**。

因为：

> **「A 和 B 有什么不同」这个整句，chunk[2] 只答得了 A 那一半，chunk[3] 只答得了 B 那一半 —— 严格说两个都答不了整句。**
> reranker 给了 A 段 0.99，因为它是查询里的**第一个主体**、更「像」答案。

**所以这不是排序问题，也不是阈值问题 —— 是「这个查询本身就不该整句拿去检索」。**

#### ⚠️ 顺便证明「调阈值」是一条死路

要「保留 chunk[0]、砍掉 chunk[1]」，阈值必须落在这两个数之间：

```
chunk[0]（正确）  0.9995
chunk[1]（邻居）  0.9990
                  ↑ 阈值得卡在 0.9990 ~ 0.9995 之间，区间宽 0.0005
```

而 chunk[3] 被砍是因为它低于 **0.3**。

**一个旋钮要同时做到「卡到小数点后四位」和「放到 0.3 以下」—— 不可能。**

> **分数饱和之后，阈值就失去了分辨能力。** 这不是「调得不够好」，是**这个零件在判定层上不解决问题**。

### 第 5 课：对照实验 —— 查询分解

#### 发现系统里本来就有这个功能

`main.py:147`：

```python
def search(query, ...):
    """【多查询】分解 → 逐个子查询检索 → 合并去重

    目的：解决「复合问题」——一个问题含多个概念时，
          单个查询向量会被稀释，导致某些概念检索不到。
    """
    sub_queries = decompose(query) if use_decompose else [query]
```

**它的 docstring 一字不差地描述了刚诊断出的症状。** 而 MCP 服务调它时 `smart_query` **默认是 `False`**。

#### 对照实验设计

**只改一个变量**：有没有查询分解。

```python
RETRIEVERS = [
    ("单查询（现在的默认）", lambda q: R._retrieve(q)),
    ("带查询分解（全开）",   lambda q: R.search(q, use_decompose=True)),
]
```

#### 结果（训练集）

| 指标 | 单查询 | 带分解 | 变化 |
|---|---|---|---|
| 召回 | 0.91 | **1.00** | +0.09 ✅ |
| MRR | 0.95 | **1.00** | +0.05 ✅ |
| 拒答 | 7/8 | **8/8** | +1 ✅ |
| 精确 | 0.76 | 0.76 | 持平 |

#### 它比预测的**多治了一条**

预测会救回 2 条多概念。**实际救回 3 条** —— 连「Langfuse 哪个便宜」也一起治好了：

```
[多概念]   多 Agent 协作和 RAG    [2]  →  [2, 3]   ✅
[多概念]   记忆机制和 RAG         [4]  →  [4, 3]   ✅
[近似无答案] Langfuse 哪个便宜     [5]  →  空       ✅ 正确拒答
```

**为什么第三条也被治好了？** 因为「Langfuse 和 LangSmith 哪个便宜」**也是一个复合问题**（两个工具名）。拆成两个子查询之后，**两个都答不了 → 合并起来是空的 → 正确拒答。**

> **我之前的诊断错了一半**：我把它归成「阈值边界太紧」，**那只是表象；病根和那两条多概念是同一类。**

#### 「改善」和「变坏」都能精确归因

11 条有答案查询的精确率之和：**8.33 → 7.83**。而只有**一条**查询的精确率变了（`如何追踪Agent内部每一步` → 多带了 `chunk[0]`）：

```
0.50 ÷ 11 = 0.045 ≈ 0.05    ← 和总体差值完全对应
```

**不是「感觉好点了」，是「这一条好了、那一条坏了，别的都没动」。**

### 第 6 课：留出集 —— 判决

#### 为什么要它

> **我们用这 19 条题设计了规则，又用这 19 条题给规则打分。**
> **这就像自己出题、自己考、自己打分。**

#### 三条纪律

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | 写的时候不参考评测结果 | 不能「挑几条规则一定会失败的」 |
| 2 | **跑完不回头改规则再测同一批** | 否则留出集就变成了训练集 |
| 3 | **结果不好就承认规则不行** | 而不是「那我再加几个关键词」 |

**第 2、3 条是留出集的全部意义。一个可以反复调整的留出集，等于没有留出集。**

#### 「智能分解」的想法

`decompose` 对**每条**查询都调一次 LLM（即使结果是「原样返回」）。所以用一条**文字规则**预判像不像复合问题，可疑的才调 LLM：

```python
COMPOUND_MARKERS = ("和", "与", "、", "以及", "还有", "对比", "区别",
                    "有什么不同", "哪个", "分别")

def looks_compound(query):
    return any(m in query for m in COMPOUND_MARKERS)
```

**为什么用文字规则而不是检索分数**：诊断数据显示，复合查询在精排分上也是「一个段落一枝独秀」（0.9881 vs 其余 <0.01），**和单概念查询长得一模一样** —— 分数判别不了。

#### 留出集的设计：四类对抗样本

| `kind` | 特征 | 期望 |
|---|---|---|
| 对抗-真漏判 | 需要 2 段以上，但文字里**没有**并列标记 | 规则会漏 → 质量下降 |
| 对抗-假漏判 | 看着像复合，其实答案**就在同一段** | 规则不命中**才是对的** |
| 对抗-命中 | 需要 2 段，且文字里**有**并列标记 | 规则应该命中 |
| 对抗-误判 | 就是单概念，但文字里**恰好有**并列标记 | 规则白花一次 LLM |

**「假漏判」这一类是最值钱的** —— 它说明：

> **「文字上像复合问题」和「需要拆开检索」不是一回事。**

（例子：「Agent 的两个评测方法各有什么优势」→ 两种方法**都写在 chunk[6] 里**，拆开反而可能丢。）

#### 判决：规则**没有通过**

```
策略                        召回      精确    MRR        拒答
单查询（现在的默认）              0.86    0.91    0.93       0/0
带查询分解（全开）               1.00    0.95    1.00       0/0
智能分解（规则预筛）              0.93    0.91    1.00       0/0

智能分解的 LLM 调用：4/14 条查询（29%）
```

**两条「真漏判」全军覆没**（召回 0.50 vs 全开 1.00），而且「对抗-命中」里有一条特别戏剧：

```
RAG 与 记忆机制 对照有什么优势    gold=[3,4]
   单查询：取到[]       召回 0.00   ← 完全失败，两段都被阈值砍了
   全开：  取到[3, 4]   召回 1.00
```

#### ⭐⭐ 训练集和留出集给出了**不同**的答案

| 数据集 | 单查询召回 | 全开召回 | 智能召回 | 结论 |
|---|---|---|---|---|
| **训练集**（19 条） | 0.91 | 1.00 | **1.00** | 「智能和全开**一样好**，成本只要 21%」 |
| **留出集**（14 条） | 0.86 | 1.00 | **0.93** | 「智能**明显差一截**」 |

> **在训练集上，智能分解和全开一模一样。在留出集上，差了 0.07。**
> **如果没有留出集，我们会带着一个错结论去改生产代码。**

**这就是留出集存在的全部理由 —— 它抓到了训练集看不见的差距。**

#### 一个设计疏漏（要记下来）

留出集的 `拒答` 一列是 **0/0** —— **一条「应该拒答」的查询都没有。**

是我设计类别时漏了：只顾着测「拆不拆」，忘了测「该不该答」。**所以这份留出集验不了「拒答」这个能力。**

不是坏结果（留出集本来就该小、该聚焦），但**要知道它的盲区在哪** —— 否则你会以为「拒答没问题」，其实只是**没测**。

### 第 7 课：落地 —— 并且看清失败的原因

#### 先量成本

写 `measure_decompose.py`，对留出集 14 条各跑一次：

```
共 14 次调用
  平均     0.70s
  中位数   0.71s
  最慢     0.99s

  拆出多个子查询的：9/14 条（64%）
```

#### C 的答案：**不需要优化**

**平均 0.7 秒，换来留出集召回 0.86 → 1.00。**

> **优化一个 0.7 秒的调用，是过早优化。**

#### ⭐⭐ 但这一跑真正的收获在输出里

**这是整个过程中第一次看到 `decompose` 的输出。**

##### 发现 1：它实际拆了 **9/14**，而规则只预测了 **4/14**

规则命中率 29%，实际需要处理的 64%。

##### 发现 2：它把「优缺点」拆成了「优点」+「缺点」

```
记忆机制的优缺点是什么
    └─ 记忆机制的优点
    └─ 记忆机制的缺点
```

**「优缺点」是一个词，里面藏着两个含义。** 真实用户经常这么问（「有什么利弊」「优劣」）。

**任何关键词规则都不可能捕捉这个** —— 它不是并列结构，是**词内部的两个意思**。

##### 发现 3：它不只是「拆」，还会**改写**

```
多 Agent 协作的机制是什么
    └─ 多 Agent 协作机制          ← 不是原查询！

RAG 的优势是什么
    └─ RAG 的优势                 ← 去掉了「是什么」
```

**这解释了那条最奇怪的样本**：

```
[真实] 多 Agent 协作的机制是什么    gold=[2]
   单查询：取到[2, 4]   精确 0.50
   全开：  取到[2]      精确 1.00
```

查询被改写成「多 Agent 协作机制」之后**更聚焦了，邻居 chunk[4] 不再混进来** —— 精确率 0.50 → 1.00。

**它救的不是「漏」，是「多」。**

#### 所以规则为什么必然失败 —— 有两条铁证

| `decompose` 实际在做什么 | 文字规则能做到吗 |
|---|---|
| 按连接词拆分（「A 和 B」） | ✅ 能 |
| **把「优缺点」拆成「优点」+「缺点」** | ❌ **做不到** |
| **把「…的机制是什么」改写成「…机制」** | ❌ **做不到** |

**规则不是「关键词不够全」，是这个任务本身超出了规则的能力范围。**

上一课靠留出集**发现**了规则不行；这一课**看清了为什么不行**。两件事合起来才完整 —— **只知道「不行」，你下次会想「那我再加几个词试试」；知道「为什么不行」，你才不会再去撞这堵墙。**

#### 落地

`mcp/mcp_server.py`，`smart_query` 默认值 `False` → `True`，并把依据写进代码注释：

```python
    # ⚠️ smart_query 默认改成 True 的依据（留出集 14 条实测）：
    #      关闭：召回 0.86  精确 0.91
    #      开启：召回 1.00  精确 0.95
    #    代价：每次检索多约 0.7 秒（一次 LLM 调用）。
    #    这个交换比很划算 —— 而且「查询分解」不只是拆复合问题，
    #    它还会【改写查询】（例如「…的机制是什么」→「…机制」），
    #    这一层收益靠任何关键词规则都拿不到（实测过，规则版在留出集上失败）。
    smart_query: bool = True,
```

## 四、关键问题专题

### 专题 1：四个指标各管一只眼睛

| 指标 | 一句话 | 坏了会怎样 | 完全看不见 |
|---|---|---|---|
| **召回** | 该找到的，找到了几成 | 回答不出来（资料明明有） | **多给的** |
| **精确** | 返回的，几成是需要的 | 回答里混进噪音 | **漏了的** |
| **MRR** | 对的排第几 | 排太靠后，被 `max_k` 截掉 | 前后的噪音 |
| **拒答** | 该说「不知道」时说了没有 | **硬答 → 幻觉** | 答得对不对 |

**实测证据**：「直接」类召回 1.00、MRR 1.00 —— **在加精确率之前，那个 0.46 是个黑洞。**

> **指标少一个，就少一只眼睛。坏掉的地方你看不见，还以为一切都好。**

### 专题 2：分数饱和之后，阈值失去分辨能力

精排分挤在 0.999 和 0.000 两极。后果：

| 后果 | 说明 |
|---|---|
| 阈值「怎么定都一样」 | 0.1 到 0.9 之间任何值结果相同 → **它从没被考验过** |
| 「分差」失真 | chunk[0] vs chunk[1] 在 logit 空间差 0.7，概率空间只差 0.0005 |

**这不是「调得不够好」，是判定层的问题得在别的零件上解。**

### 专题 3：同一旋钮，两个方向

| 问题 | 想要 | 
|---|---|
| 精确低（邻居混进来） | 阈值**调高** |
| 召回漏（该有的被砍） | 阈值**调低** |

**而更深一层：要「保留 0.9995、砍掉 0.9990」，阈值得卡在 0.0005 宽的区间里 —— 这个旋钮根本没有这个精度。**

### 专题 4：我的预测被数据推翻了三次

| # | 我的预测 | 实际 | 为什么错 |
|---|---|---|---|
| 1 | 精排分是 logits，会有负数 | 是 Sigmoid 后的**概率** | 版本默认值变过（`model.py:425`） |
| 2 | 「近似无答案」会被高高兴兴返回 | **5/6 正确拒答** | cross-encoder 对「明显缺细节」的问题是**准确**的 |
| 3 | 返回的一半是「垃圾」 | 是**同域邻居**（对比资料），危害轻得多 | 过度解读了精确率 |

**第 2、3 条的共同原因：我当时看的指标里没有精确率。**

> **凭直觉猜「哪里会坏」，猜错是常态 —— 这就是必须先建评测的理由。**

### 专题 5：尺子本身也要被检查 —— 三个层次

| 层次 | 坏法 | 本项目的实例 | 怎么发现 |
|---|---|---|---|
| **刻度值** | `gold` 标错 | 8 条全填 `[0]`，5 段从没被考过 | 统计 **gold 分布** |
| **刻度选择** | 指标漏了 / 指标饱和 | 漏了精确率；`Recall@5` 在 7 段上结构性饱和 | 摊开逐条结果看；想「这个指标在什么情况下会变」 |
| **量的对象** | 测的不是真正在用的那条路 | 评测调 `_retrieve`，而 MCP 服务调 `search`（虽然 `smart_query=False` 时等价） | **去读真正在用的调用点** |

**三个层次都坏过一次，而且都不报错。**

### 专题 6：留出集 —— 自己出题自己考

| | 训练集 | 留出集 |
|---|---|---|
| 用途 | 设计和调优，看多少遍都行 | **只看一次，看完定论** |
| 纪律 | — | 不参考结果设计、跑完不改规则、结果不好就认 |

**本项目最有说服力的证据**：

| 数据集 | 全开召回 | 智能召回 |
|---|---|---|
| 训练集 | 1.00 | **1.00**（看不出差别） |
| 留出集 | 1.00 | **0.93**（差 0.07） |

**没有留出集，会带着错结论上生产。**

### 专题 7：评测本身有噪声

`search(use_decompose=True)` 内部用 LLM 拆分，**同一策略、同一评测集，两次跑出不同的数字**：

| | 第一次 | 第二次 |
|---|---|---|
| 总体精确 | 0.71 | 0.76 |
| 换词精确 | 0.75 | 0.88 |

**差异 0.05，来自一条查询** —— 而我们在比较的差异**也是 0.05 量级**。

> **噪声的量级和你关心的差异量级一样大时，单次运行的数字不能当结论。**

由此：

| 说法 | 站得住吗 |
|---|---|
| 「智能 MRR 0.95 vs 全开 1.00，所以全开排序更好」 | ❌ 差的 0.05 来自一条查询，噪声也是 0.05 |
| 「智能召回 0.91 → 1.00」 | ✅ 差 0.09，来源清楚（那两条多概念） |
| 「LLM 调用从 19 次降到 4 次」 | ✅ 确定数，不含噪声 |

### 专题 8：用 LLM 做「理解」，用规则做「执行」

这条在 MCP 那一课已经出现过一次。这里再次验证：

| 做法 | 结论 |
|---|---|
| 用 LLM 判断「要不要拆」+ 拆 | ✅ 准，但每次 0.7 秒 |
| 用关键词规则判断「要不要拆」 | ❌ 留出集上失败 —— 因为真正的工作是**理解**（词内含义、改写），不是**匹配** |

**「智能分解」的失败不是「关键词不够全」，是**把「理解」的任务交给了「匹配」**。**

（但也别反向过头：0.7 秒的 LLM 调用在质量收益面前**不值得优化** —— 这是过早优化。）

### 专题 9：把依据写进代码

`smart_query` 的默认值从 `False` 改成 `True` 时，**把实测数字和「为什么规则替代不了」一起写进了注释**。

因为：

- 三个月后看到 `smart_query: bool = True` 的人（包括你自己）只会想「为什么默认开？是不是随便定的？」
- **默认值的依据不写在它旁边，就等于没有依据** —— 下一个人可能随手改回去

> **和「错误信息是操作说明」是同一个道理：代码里每个「反直觉的默认值」都应该自带解释。**

## 五、踩坑总结表

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `ModuleNotFoundError: No module named 'main'` | `python retrieval\diagnose.py` 时 `sys.path[0]` 是 `retrieval\`；`python -m retrieval.diagnose` 时才是项目根 | 用 `-m`；或在脚本顶部加 `sys.path.insert(0, 项目根)` |
| 2 | `from research_agent import main as R` 报错 | 项目根**不是包**（没有 `__init__.py`），而且它的父目录不在 `sys.path` 上 | 用 `import main as R` + 引导 `sys.path` |
| 3 | 评测集 8 条 `gold` 全是 `[0]` | 从模板复制 `query` 时忘了改 `gold` | **体检工具统计 gold 分布** —— 一眼看出 chunk[0] 占 11/16 |
| 4 | 评测「看起来很好」，实际一半是噪音 | 指标漏了**精确率** | 补上；并问「这个指标在什么情况下会变坏」 |
| 5 | `Recall@5` 永远是 1.00 | 7 段语料、粗筛取 20 → 候选池就是全集，唯一门是阈值 → **结构性饱和** | 别只看它；或换更有分辨力的指标 |
| 6 | 以为「分数是 logits」，预测会有负数 | `sentence-transformers 6.1.0` 对 `num_labels==1` **默认套 Sigmoid**（`model.py:425`） | 读源码确认，别信记忆里的默认行为 |
| 7 | 评测两次跑出不同数字 | `decompose` 用 LLM，**本身有随机性** | 重复跑；或固定/缓存 decompose 结果 |
| 8 | 想「调阈值」同时解决精确和召回 | 分数饱和，阈值没有 0.0005 的精度 | **别修阈值**，去动别的零件 |
| 9 | 对照实验里「全开」和「智能」在训练集上完全一样 | **过拟合** —— 规则是从这批数据里看出来的 | 用**留出集**（没参与设计的 14 条） |

## 六、经验教训

### 1. 先建尺子，再动手

没有评测，一切优化都是猜。而且**猜错是常态** —— 本次我的预测被推翻三次。

### 2. 「结果正确」和「你的机制在起作用」是两件事

第 4 课的 `id=3 = False`（写操作项目）和第 6 课的对比实验是同一个道理：**只有把机制拆掉看到结果变坏，才能说这两者有因果。**

### 3. 尺子本身要检查 —— 三个层次

**刻度值**（gold 分布）、**刻度选择**（指标够不够、饱不饱和）、**量的对象**（是不是真正在用的那条路）。

三个都坏过一次，而且都不报错。

### 4. 指标少一个，就少一只眼睛

召回 1.00 把精确 0.46 完全盖住了。**坏掉的地方你看不见，还以为一切都好。**

### 5. 数字要能精确归因

「精确率掉 0.05」→ 追到**一条查询**上，`0.50 ÷ 11 = 0.045`。**不是「感觉变了」，是「这一条变了，别的都没动」。**

### 6. 留出集是唯一能挡住过拟合的东西

**自己出题、自己考、自己打分** —— 分数当然好看。而留出集抓到了训练集看不见的 0.07。

**而且纪律②（跑完不改规则）比纪律①更重要**：允许反复调整的留出集，等于没有留出集。

### 7. 噪声和差异同量级时，单次结果不能当结论

LLM 驱动的环节会给评测带来 0.05 量级的抖动。**先把「确定性数字」（LLM 调用次数）和「有噪声的数字」（指标）分开看。**

### 8. 「看起来像」和「实际是」是两件事

- 「文字上像复合问题」≠「需要拆开检索」（对抗-假漏判）
- 「相关」≠「能作答」（精确率问题的根源）
- 「分数很低」≠「不相关」也可能是「饱和到 0」

### 9. 用 LLM 做理解，用规则做执行

关键词规则替代不了 `decompose` —— 因为真正的工作是**理解**（词内含义、查询改写），不是**匹配**。

**但也别反向过头**：0.7 秒的 LLM 调用在质量收益面前不值得优化 —— **那是过早优化**。

### 10. 把依据写进代码

`smart_query: bool = True` 旁边必须有实测数字和「为什么不能用规则替代」。**默认值的依据不写在它旁边，就等于没有依据。**

### 11. 失败要留档

这次的 commit message 里**特意记下了失败的那条**：

### 容易忘的细节

- **`-m` 和直接跑文件，`sys.path[0]` 不一样** —— `python file.py` 是**文件所在目录**，`python -m pkg.mod` 是**当前工作目录**。所以必须在项目根目录用 `-m`。
- **每次跑要先加载两个模型**（约 30 秒）。
- **`decompose` 用 LLM，结果有随机性** —— 同一个查询两次跑可能拆出不同的子查询，所以**评测数字本身有 0.05 量级的抖动**。
- **`search(use_decompose=True)` 比 `_retrieve` 慢约 0.7 秒**。
- **改了 `mcp/mcp_server.py` 后，Cursor 里的 MCP Server 不会热重载** —— 要重启（第一次调用前等约 30 秒模型加载），日志里应出现 `优化=True`。
